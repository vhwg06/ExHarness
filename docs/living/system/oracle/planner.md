# Oracle retrieval planner

Source-synchronized projection of `packages/oracle/src/planning-strategies.js` and `scripts/oracle-context-intelligence/planner-ablation.mjs`. Open Oracle questions live only in `../docs/blackboard/state.md`.

## Delivered strategies

`createRetrievalPlanner` in `packages/oracle/src/retrieval-planner.js` is the unchanged default (`DETERMINISTIC_V1`): it reserves work per evidence and stops at the first successful provider. Two opt-in strategies live in `packages/oracle/src/planning-strategies.js` and keep the delivered `{ plan, execute }` interface:

```text
packages/oracle/src/planning-strategies.js
 -> createFusionRetrievalPlanner({ catalog, base })        RRF_FUSION_V1
 -> createGraphExpandedRetrievalPlanner({ catalog, base, graphProviderId, repositoryRef })  GRAPH_EXPANDED_V1
```

Both delegate every reservation to the base planner, so `plan()` is identical to the default for the same requirement and options, and every candidate is validated by `SourceCatalog` with the same `EXACT`/`CURRENT`, provenance and budget rules.

- **RRF_FUSION_V1:** executes every reserved work unit for an evidence instead of stopping at the first success, then orders candidates by reciprocal-rank fusion: each provider contributes `1 / (60 + rank)` per candidate where rank is the 1-based position in that provider's accepted list, summed across providers. Ties break by `itemRef` ascending. Duplicates merge to one candidate per `itemRef`, so an item returned by two providers outranks singletons. The accepted count stays within the reserved item budget.
- **GRAPH_EXPANDED_V1:** runs the base plan unchanged, then — when unreserved budget remains and a `CONTEXT_GRAPH` provider supporting `TRAVERSE_GRAPH` is registered — adds at most one `IMPORTS` hop per resolved `REPOSITORY` evidence, anchored at that evidence's top base candidate and reserved only from budget the base plan left unreserved. Graph-derived items keep `AUTHORITATIVE_SOURCE` provenance and are validated by `SourceCatalog` against a derived requirement. Base candidates are unchanged and come first. The hop is skipped with `BUDGET_EXHAUSTED` when no unreserved budget remains, and with `NO_GRAPH_PROVIDER` when no graph provider is registered.

Import path: consumers import `packages/oracle/src/planning-strategies.js` directly. The strategies are deliberately not re-exported from `packages/oracle/src/index.js`, whose export list is pinned by the architecture boundary.

## Ablation cohort

`scripts/oracle-context-intelligence/planner-ablation-cohort.json` freezes the comparison ground truth:

- `snapshotRef`: the exact commit every arm runs against; `repositoryRef`: `exharness`.
- `corpusRoots`: `packages/oracle/src` and `packages/agentic-system/src`.
- One query per component of the component registry: `query` is that component's `contractRefs` joined by one space, and `relevant` is the sorted list of its concrete `.js` `sourceRoots` that exist at the snapshot and lie under the corpus roots. Components with no such file are listed under `excluded` with a reason. Nothing is hand-labelled.
- Budget `{ maxItems: 3, maxProviderCalls: 3, maxMaterializedBytes: 24576, maxResolutionSteps: 1 }`, `k: 3`, thresholds `{ minMeanRecallGain: 0.05, maxBytesRatio: 1.25, perQueryNonInferior: true }`, and a recall definition (`Recall@k` over top-k selected distinct `itemRef`s, plus MRR).
- `cohortDigest`: SHA-256 over the canonical JSON of `{ snapshotRef, corpusRoots, queries, excluded }`.

The cohort is generated by the harness itself (`--mode cohort --write`), which reads the registry at the snapshot through `git show`, never the working tree. Before any arm runs, the harness regenerates the cohort at the committed snapshot and compares queries, excluded set and digest; any mismatch aborts with `COHORT_DIGEST_MISMATCH`, so a hand-edited relevant set cannot run.

## Arms and metrics

Every arm executes one `REQUIRED` `REPOSITORY` evidence per query (`EXACT` snapshot, cohort budget) through `SourceCatalog` and planner `execute()`:

- **A0** `DETERMINISTIC_V1` (default planner, all providers).
- **A1** lexical-only and **A2** symbol-only, via the delivered `unavailableProviders` option (diagnostic arms, never candidates for recommendation).
- **A3** `RRF_FUSION_V1`.
- **A4** `GRAPH_EXPANDED_V1` with repository `exharness`.

Per arm and query the harness records the selected ordered distinct `itemRef`s, `Recall@k`, MRR, materialized bytes (sum of JSON-encoded candidates), provider calls (planned work plus graph expansion calls) and unresolved reasons, plus mean recall, mean MRR and mean bytes per arm. If every arm selects identical ordered `itemRef`s for every query, the comparison is non-discriminating by construction.

## Preregistered reducer and recorded decision

The reducer is a pure function of the report arms, per-query results and cohort thresholds. A candidate arm (A3/A4 only) is eligible when every query recall is at least the A0 recall, mean recall beats A0 by `minMeanRecallGain` (0.05), and mean bytes stay within `maxBytesRatio` (1.25) of A0. The best eligible arm by mean recall then MRR yields `RECOMMEND_<strategyId>`; otherwise the outcome is `KEEP_DETERMINISTIC_V1`. A non-discriminating report yields `INCONCLUSIVE_NON_DISCRIMINATING`. `--mode validate --report <file>` re-reduces a recorded report and exits nonzero when the decision differs. Model-assisted planning is `NOT_EVALUATED`: no model call takes part in any strategy, fixture or decision.

Recorded run at the frozen snapshot (`be9afd2e559c030942447eed02fb21157a95b109`, cohort digest `e6850e3e14251c5211be3d2b728edf531cf004fdaa158ac761bdc65f13cb8634`, 6 queries, 11 excluded):

```text
arm  strategy            mean Recall@3  mean MRR  mean bytes  provider calls
A0   DETERMINISTIC_V1    0.0000         0.0000    1717.0      12
A1   lexical-only        0.0556         0.1667    1775.2       6
A2   symbol-only         0.0000         0.0000     233.8       6
A3   RRF_FUSION_V1       0.0556         0.0833    2009.0      12
A4   GRAPH_EXPANDED_V1   0.0000         0.0000    2676.8      18
```

Only the infrastructure query discriminated on recall: fusion kept the symbol-first hit and added the lexical hit that names the component source, lifting that query from 0.000 to 0.333 while matching the baseline everywhere else (gain +0.0556, within the byte ratio at 1.17). Graph expansion added import neighbours that cost bytes without recall (ratio 1.56). Decision: **RECOMMEND_RRF_FUSION_V1**. The default planner is unchanged; promotion to default would require held-out acceptance outside this task.

## Fixture-client limits

The lexical client is a deterministic token-overlap scorer (query and file identifiers split into lowercased camelCase sub-tokens; score is the count of distinct shared sub-tokens, ties by path, snippets capped at 1200 chars). The symbol client is an exported-identifier index (`export function/class/const/let/var` names and `export { A, B as C }` targets, exact whole-token match in query-token order then path). Both are snapshot-bound fixtures returning the frozen revision as their `REVISION` validator; they are not Zoekt, LSP, or any live index, and absolute recall numbers reflect fixture quality, not production retrieval quality. Reproduce with `node scripts/oracle-context-intelligence/planner-ablation.mjs --out <file>` and check with `--mode validate --report <file>`.
