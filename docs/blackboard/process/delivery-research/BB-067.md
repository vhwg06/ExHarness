# BB-067 — Enforce bounded workspace and tool capabilities

Status: RESEARCH INPUT; no implementation authority.

## Outcome

Agent execution is constrained to its authorized workspace, tools, network and budget with enforceable cancellation.

## Current gap

Real code execution introduces filesystem, credential and side-effect boundaries not proven by abstract authority tests. BB-066 selects a real OpenHands coding-agent runtime, but its local driver and TerminalTool are intentionally not a sandbox boundary.

## Threat model

The model, repository content, shell commands and MCP metadata are untrusted. Assume a successful prompt-injection can make TerminalTool execute arbitrary shell commands.

Protected assets are the host filesystem outside the one attempt workspace, sibling workspaces, verifier/control-plane files, the Docker socket and daemon authority, raw provider/SCM/MCP credentials, capability grants, approval receipts and Blackboard/Oracle publication authority.

Trusted computing base for the first supported profile is the ExHarness host orchestrator, Docker Engine, gVisor runsc, the attempt-scoped credential/capability proxy and the independently verified runtime image. Missing or drifting TCB identity is BLOCKED; there is no silent fallback to a host process or weaker container runtime.

## Alternatives

### Isolated local process — rejected

A local process cannot establish the filesystem or credential boundary. OpenHands TerminalTool is a shell executor; working-directory convention and prompts do not stop absolute-path reads, sibling-workspace access, environment inspection or arbitrary outbound network calls.

### Bare OpenHands DockerWorkspace — rejected as the enforcement boundary

The exact BB-066 OpenHands commit provides DockerWorkspace and RemoteWorkspace primitives, but DockerWorkspace forwards selected host environment values with `-e KEY=value`, permits arbitrary volumes/network selection and its generated `docker run` does not itself pin the BB-067 hardening set (read-only root, capability drop, no-new-privileges, CPU/memory/PID ceilings or deny-by-default egress). It is useful source evidence, not sufficient policy enforcement.

### Docker Sandboxes / sbx — benchmark, not selected dependency

Docker Sandboxes 0.43.0 (2026-09-15) demonstrates a strong target model: microVM isolation, network policy and host-side credential proxy. It is not selected because its public release repository is proprietary and below the project >=1,000-star source threshold. ExHarness copies the architectural lesson, not the dependency.

### Managed OpenHands workspace — rejected for the first profile

Managed remote workspaces add external account/service lifecycle and a second operational boundary without reducing the first local delivery profile's required authority logic. The first supported profile stays self-hosted and reproducible.

## Enforcement design

1. Build an immutable BB-067 runtime image from the exact BB-066 Python lock, OpenHands driver and agent-server/runtime dependencies. No package manager or Git network access is required during an attempt.
2. Launch it through Docker with `--runtime=runsc`, no privileged mode, no Docker socket, no host PID/IPC, dropped Linux capabilities, `no-new-privileges`, read-only root, tmpfs only for declared scratch paths, and explicit CPU/memory/PID limits.
3. Mount only the attempt-specific prepared agent workspace read-write plus a dedicated attempt state volume. Do not mount repository root, verifier workspace, Blackboard, Oracle store or host credential files. Host validates the mount list before create and validates changed paths after execution.
4. Attach the container only to a Docker `--internal` network. It has no default route to arbitrary external networks. The host exposes one attempt-scoped provider proxy on that internal bridge.
5. The real provider credential remains only in the trusted host process. The container receives a random attempt capability token and proxy base URL. The proxy validates attempt/generation/profile, strips any agent-supplied authorization, injects the real provider credential upstream, meters model calls/tokens/cost and refuses any origin/path outside the immutable model profile.
6. The capability token is not an account credential: it is scoped to one executionAttemptId, one provider origin/model profile, hard budgets and a short lifetime; it is revoked on terminal completion/invalidation.
7. OpenHands still constructs only TerminalTool and FileEditorTool. An immutable ExecutionCapabilityGrant outside the agent workspace declares every tool/MCP capability the attempt may call. Repository text, tool descriptions, tools/list responses and model output are data and cannot extend the grant.
8. Protected mutating operations are host-side capabilities. A future MCP call must match grant {serverRef, method, name, audience} and any required approval receipt before transport dispatch. MCP 2026-07-28 has no protocol session identity, so ExHarness binds authorization to executionAttemptId + claim generation + capabilityGrantRef, never Mcp-Session-Id or self-reported clientInfo.
9. Oracle remains a trusted read/materialization boundary. Source/context is materialized before sandbox execution; Oracle credentials/adapters are not mounted or exported into the agent shell. Mutating delivery capabilities stay separate from Oracle reads.
10. Wall-clock cancellation is owned by DomainExecutionController/adapter AbortSignal; max iterations remains in OpenHands; model-call/token/cost ceilings are additionally enforced by the trusted provider proxy. A hit stops further dispatch, terminates the sandbox process with bounded TERM/KILL and leaves the semantic attempt RECOVERY_REQUIRED when effects may be ambiguous.
11. Recovery reuses the same executionAttemptId, conversation ID, workspace/state volume and immutable sandbox-policy/image/grant hashes. A replacement container is allowed only as a runtime process replacement under the same semantic attempt; policy/image/workspace/grant drift fails closed.
12. Runtime success remains a candidate only. The trusted host exports content-addressed Docker/runsc identity, inspect/policy digest, process result, source diff/tree hashes, budget counters and negative-probe evidence; independent acceptance/publication stays in DomainExecutionController.

## Discriminating experiment

The live probe starts from one known workspace and sibling sentinel, plus a host-only credential sentinel:

- path escape: shell attempts absolute/relative reads outside the mounted workspace and a sibling-workspace sentinel;
- host capability: shell attempts Docker socket/host process/control-plane access;
- egress: shell attempts arbitrary HTTPS/DNS target; only the provider proxy route is usable;
- credential: shell inspects env, process args, filesystem, conversation/runtime output and traces for the raw provider sentinel;
- tool injection: repository content asks the agent to add a new tool/authority; immutable grant remains unchanged;
- MCP injection: a fake untrusted MCP catalog advertises a protected mutating tool and misleading annotations; call is denied without an exact grant/approval;
- budgets: deterministic fake upstream and one credential-bearing provider run cross model-call/token/cost/time ceilings; no further dispatch occurs;
- recovery: terminate after durable activity, restart the runtime container with the same state, and reject any image/policy/grant/workspace drift.

The probe records exact Docker Engine, runsc release, image digest, container/network/mount policy digest, attempt/grant/profile identities, raw bounded outputs, source tree hashes and secret-scan result. Missing Docker/runsc/provider prerequisites are BLOCKED evidence, never synthetic success.
