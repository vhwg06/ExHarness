# BB-076 — Accept a supported release with independent value reproduction

Status: RESEARCH CONVERGED CANDIDATE — 2026-09-27.

Canonical benchmark program: `docs/blackboard/process/harness-benchmark-program-research.md`.

## Outcome

A frozen supported release is accepted only when a clean-room installation proves exact artifact/source identity, representative delivery and lifecycle behavior, and a preregistered delivery-value comparison on the unopened release-reserve cohort.

## Research conclusion

BB-076 is release acceptance, not tuning.

Worker input must include exact DONE evidence from:

- BB-074 delivery-value study;
- BB-075 HOW promotion or keep-baseline decision;
- the supported install/distribution profile delivered upstream (transitively through the BB-074 product dependency chain);
- the exact supported harness profile published by BB-081.

Any missing/incompatible delivered contract yields `PLAN_INPUT_CONTRADICTION`.

BB-076 must not modify product behavior to make release acceptance pass.

## Release candidate freeze

Before any release-reserve model execution, freeze:

```text
source commit + git tree
supported harness/profile identity
current HOW policy identity
dependency lock digest
build/install procedure identity
builder/runtime identity
produced package/release artifact digests
benchmark protocol/profile hashes
release-reserve manifest hash
known limitations
```

After freeze, any source, lock, build recipe, supported profile, HOW policy or release-reserve mutation invalidates the run and requires a new release candidate identity.

## Clean-room reproduction

Use the exact install/runtime profile delivered by the supported distribution task. BB-076 does not redefine packaging.

The independent reproducer must start from a fresh environment with no working-tree checkout and install only the frozen release artifact(s) by digest.

It must verify:

1. artifact digest matches `SUPPORTED_RELEASE_PROVENANCE_V1`;
2. installed version/source identity matches the frozen release manifest;
3. dependency/runtime compatibility checks pass;
4. missing credentials fail with actionable diagnostics rather than partial execution;
5. representative reference delivery completes and independent QA accepts it;
6. one change/recovery case succeeds before paid release-reserve execution is opened.

A clean-room run may use the same repository's verification tooling, but it must consume only published release artifacts/manifests and must not read uncommitted candidate state.

## Release-reserve ownership

BB-075 seals four `RELEASE_RESERVE` task digests and is forbidden from running model arms on them.

BB-076 is the first task allowed to execute them.

Any evidence that a release-reserve model result existed before BB-076 invalidates the reserve and returns to research for a fresh disjoint partition.

## Release value reproduction

Use the same outer Harbor substrate, direct control, model/provider route, tool envelope, evaluator, resource ceilings and human-effort event semantics as BB-074.

Arms:

```text
D = exact DIRECT_CODEACT control
R = ExHarness installed from the frozen release artifact/provenance
```

Run:

```text
4 release-reserve tasks
x 2 repeats
x 2 arms
= 16 registered arm units
```

Use counterbalanced D/R order and fresh task/runtime/provider state per registered unit.

All retries and failures remain in append-only accounting.

The release task does not reuse BB-075 improvement-heldout results as release evidence.

## Release value gate

Primary release-reserve gates:

```text
quality:
  accepted units R >= D
  critical escaped defects = 0

human effort:
  total operatorActiveMs(R) <= 0.80 * total operatorActiveMs(D)

provider economics:
  providerCostPerAccepted(R) <= 1.10 * providerCostPerAccepted(D)
  cost must be known for the primary gate

safety/currentness:
  no duplicate external effects
  no stale-worker/currentness bypass
  recovery negatives pass
```

The small cohort is a bounded release acceptance check, not a statistical population claim. Report paired deltas and consistency; do not claim significance.

If the BB-075 result is KEEP_BASELINE, R uses the exact unchanged baseline HOW policy.

If BB-075 promoted a candidate, R must bind the exact promoted policy generation and prove old attempts remain pinned.

## Lifecycle reproduction on exact release

Run the supported release through the six BB-074 lifecycle scenarios on the packaged artifact, not a working-tree runtime:

```text
LOCAL_REQUIREMENT_CHANGE
CROSS_DOMAIN_REQUIREMENT_CHANGE
KILL_RESUME_DUPLICATE_ACTIVATION
STALE_WORKER_DEPLOYMENT_FENCE
CLEAN_INSTALL_REFERENCE_DELIVERY
UPGRADE_ROLLBACK_COMPATIBILITY
```

Each scenario records:

- independent acceptance;
- operator active effort;
- elapsed time;
- provider cost when live;
- recovery/fence outcome;
- failure fingerprint;
- exact release/provenance identity.

All six are required.

## Documentation/limitation consistency

Generate a machine-readable `SUPPORTED_RELEASE_MANIFEST_V1` from delivered evidence and compare it to user-facing support docs.

The manifest includes:

- supported runtime/install mode;
- supported harness profile;
- supported model/provider compatibility policy;
- credential requirements;
- persistence/upgrade/rollback guarantees;
- known unsupported provider capabilities;
- known benchmark/product limitations.

A documented feature not supported by the frozen release or a supported behavior omitted from limitations is a release failure.

## Decision reducer

Outputs:

```text
RELEASE_ACCEPTED
RELEASE_NO_GO
INCONCLUSIVE
```

`RELEASE_ACCEPTED` requires:

- release provenance and artifact/source identity verified;
- clean-room install/reference delivery accepted;
- complete 16-unit release-reserve comparison;
- all value gates pass;
- all six lifecycle scenarios pass;
- support docs/limitations match evidence;
- no dependency/profile/currentness drift.

`RELEASE_NO_GO` applies when evidence is complete and any required identity, value, lifecycle or documentation gate fails.

`INCONCLUSIVE` applies to missing registered units, unknown primary cost, provider/infra gaps preventing evaluation, invalid reserve provenance or incomplete lifecycle evidence.

No outcome may be downgraded to "release anyway with CI green".

Jev may validate evidence claims, but the release reducer outcome is deterministic.

## Implementation slices

### S1 — bind + freeze

- resolve exact DONE BB-074/075 and supported distribution/profile evidence;
- verify release-reserve has no prior model execution;
- freeze source/tree/policy/profile/build/dependency identities.

### S2 — build provenance

- produce release artifact(s);
- emit `SUPPORTED_RELEASE_PROVENANCE_V1`;
- verify artifact digests and resolved dependency identity.

### S3 — clean-room install

- start fresh supported environment;
- install only release artifact(s);
- verify manifest/provenance;
- run reference delivery + independent QA;
- run one recovery/change preflight.

### S4 — release-reserve comparison

- execute all 16 D/R registered arm units;
- preserve all attempt/provider/human-event accounting;
- apply unchanged independent evaluator.

### S5 — lifecycle reproduction

- run all six lifecycle scenarios against packaged release;
- prove recovery/currentness/install/rollback behavior.

### S6 — support contract audit

- compare `SUPPORTED_RELEASE_MANIFEST_V1` to documentation and delivered evidence;
- reject unsupported claims or missing limitations.

### S7 — deterministic release decision

- reduce to RELEASE_ACCEPTED, RELEASE_NO_GO or INCONCLUSIVE;
- update Living truth only with the verified result and limitations.

## Negative cases

Must reject or no-go:

- release artifact digest differs from provenance;
- clean-room run reads working-tree/uncommitted product files;
- runtime/profile/policy changes after release freeze;
- release-reserve result predates BB-076;
- BB-075 improvement-heldout reused as release reserve;
- missing primary provider cost treated as zero;
- fewer than 16 registered release-reserve units treated as complete;
- direct and release arms use different evaluator/tool/model/budgets;
- one lifecycle scenario omitted;
- working-tree lifecycle passes while packaged release fails;
- stale worker or duplicate effect tolerated because quality passed;
- docs claim unsupported behavior;
- CI green used as release value evidence;
- failed value gate downgraded to known limitation instead of RELEASE_NO_GO.
