# BB-096 — Bind delivered Backend/QA acceptance to a real repository and real verification processes

Status: RESEARCH INPUT; no implementation authority.

## Outcome

The delivered Backend -> QA path can run against a real local git repository through a real Core model strategy. Its mutation, typecheck, tests, behavior and regression evidence come from actual commits and executed processes bound to the evaluated revision. ACCEPT becomes impossible when the repository did not change or its tests fail.

## Current gap

This section is DELIVERED_TRUTH, established by the executed probe `docs/blackboard/evidence/BB-096/real-execution-probe.mjs`, whose result is in `real-execution-probe-result.json`.

- `packages/*/src` contains no model provider adapter. `packages/agentic-system/src` contains no process execution.
- No agentic test uses a Core model strategy (`createCodeActStrategy` / `createJavaScriptCodeActStrategy` / `createPredictStrategy`). Every Backend/QA test injects a hand-written `strategy.run()` that calls ACT -> verify -> EVALUATE -> PROMOTE in a fixed order.
- `workspace.act()` and verifiers are injected fakes. The fake workspace invents a `rev-N` revision, and the fake verifiers always return PASS.
- Discriminating experiment: a temporary git repository with one failing `node:test`, driven through `runBackendObjective` with the same injected shapes the delivered tests use.
  - Result: `completion.action = ACCEPT`, with `backend.mutation`, `backend.typecheck` and `backend.tests` all PASS.
  - Meanwhile the repository HEAD is unchanged, the working tree is clean, the real test still exits 1, and zero verification processes were spawned.
- `README.md` presents `-> mutation + typecheck + tests evidence` as delivered.
- No READY delivery plan owns this path (PLANNED_CONTRACT).
  - BB-066..068 introduce an OpenHands runtime, a sandbox and SCM through `DomainExecutionController`.
  - BB-069 reuses `QaWorker` but never binds `BackendWorker`/`BackendCompletion` to a real workspace.

## Research questions

1. What is the smallest real workspace that preserves Core lineage semantics? Options are a detached git worktree plus commits, or a copied directory plus content hashes.
2. What makes a verification record bind to the evaluated revision rather than to a label? Options are a HEAD check before execution, a tree-cleanliness check after execution, or output digests.
3. Can the delivered BackendWorker run a real Core strategy, CodeAct with a deterministic model, without changing Core or completion policy?
4. How do timeouts terminate the verification process tree on POSIX and on Windows, without a shell?

## Approaches and evidence

- **Workspace.** A detached git worktree gives real commit identities that `candidate.version` can carry. It leaves the source repository HEAD and working tree untouched. A copied directory with content hashes was rejected: it has no stable revision identity and no reviewable diff.
- **Verifiers.**
  - Selected: a local command verifier that uses `spawn` with an argument array (`shell: false`). It checks HEAD against `candidate.version` before running and checks tree cleanliness after.
  - Rejected: a shell-string runner, because of the injection risk.
  - Rejected: CI polling. BB-068 owns CI.
- **Strategy.** `createHarness({ strategy })` composes `createAgentRuntime({ strategy })`, and CodeAct `CAPABILITY` actions go through the runtime's `invoke(name, input)`. A deterministic model adapter can therefore drive AVO ACT, verify, EVALUATE and PROMOTE through a real Core strategy. A live provider is BB-066's scope.
- **Isolation.** These adapters are trusted local fixtures, not a sandbox. Enforcing isolation remains BB-067's responsibility.

## Discriminating experiment

| Case | Required result |
|---|---|
