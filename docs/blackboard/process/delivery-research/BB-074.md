# BB-074 — Controlled delivery-harness value benchmark research

Status: RESEARCH CONVERGED CANDIDATE — 2026-09-27.

Canonical benchmark program: `docs/blackboard/process/harness-benchmark-program-research.md`.

BB-074 asks whether the supported ExHarness delivery product improves software-delivery economics and human effort at comparable independently accepted quality. It consumes the calibrated benchmark substrate, harness isolation/profile evidence and the delivered change/recovery/distribution capabilities; it does not redefine them.

## Experiment structure

Use two evidence layers.

### A. Matched external comparison

Compare:

```text
D = BB-077 DIRECT_CODEACT
E = exact BB-073 supported ExHarness delivery release
    using the BB-081 supported Core profile
```

Hold fixed:

- model/provider;
- task digest/instruction;
- starting environment;
- tool surface;
- aggregate cost/token/turn/time ceilings;
- reset policy;
- final Harbor verifier.

Only delivery orchestration differs.

The external cohort is new relative to BB-077/081:

```text
primary:
  configure-git-webserver
  git-multibranch
  build-cython-ext
  modernize-scientific-stack
  custom-memory-heap-crash
  sqlite-with-gcov

ordered reserves:
  openssl-selfsigned-cert
  db-wal-recovery
```

All tasks bind Terminal-Bench 2.1 source commit `7131e4375048a0e408a8fb404b5f499d726b695b` and exact digests from its dataset manifest.

Before any live arm result, every used task must pass oracle 5/5 and nop fail 1/1. A failed primary may be replaced only by the next ordered reserve before the cohort is sealed.

Run two repeats per task and arm:

```text
6 tasks × 2 repeats × 2 arms = 24 registered arm units
```

Counterbalance D/E order by task and repeat. Each registered unit gets a fresh Harbor environment, arm runtime/product state and provider session. Retries remain append-only attempts inside the same unit.

Per-unit aggregate ceilings are identical for D and E:

```text
provider cost <= USD 1.20
input tokens  <= 360,000
output tokens <= 24,000
model turns   <= 24
host calls    <= 96
wall time     <= 1,800 s
```

The live external cohort ceiling is USD 35.

### B. Product lifecycle evidence

Do not invent a symmetric direct-agent workflow for capabilities the product uniquely provides.

After BB-071 and BB-073 are delivered, run:

```text
LOCAL_REQUIREMENT_CHANGE
CROSS_DOMAIN_REQUIREMENT_CHANGE
KILL_RESUME_DUPLICATE_ACTIVATION
STALE_WORKER_DEPLOYMENT_FENCE
CLEAN_INSTALL_REFERENCE_DELIVERY
UPGRADE_ROLLBACK_COMPATIBILITY
```

Each scenario reports independent acceptance, operator-active time, elapsed time, provider cost when live, recovery/fencing result and failure fingerprint.

Missing or incompatible delivered lifecycle semantics are a plan-input contradiction, not a skipped passing scenario.

## Human effort protocol

Do not infer active effort from terminal time, tool calls or provider waits.

Every run uses `DELIVERY_HUMAN_EVENT_V1`.

Included in primary effort:

```text
OPERATOR_REVIEW
PRODUCT_DECISION
COORDINATION
MANUAL_EDIT
```

Excluded:

```text
BENCHMARK_SETUP
INDEPENDENT_EVAL
PASSIVE_WAIT
```

Events use explicit START/PAUSE/RESUME/STOP. A zero-effort run requires `NO_INTERVENTION`. Included intervals are unioned so overlapping categories are not double-counted, and active included intervals may not overlap across registered units.

Manual edits are allowed as observable human intervention, but must bind the changed artifact/commit and mark the delivery `humanAssisted=true`. They never bypass the independent final verifier.

Optional perceived-ease/confidence ratings are diagnostic only. They cannot override observed active time, quality or cost. This follows the research warning that perceived AI speedup can diverge from observed completion time.

## Value profile

Report separately:

```text
accepted quality
provider cost / accepted delivery
operator active minutes
elapsed lead time
repeat consistency
failure fingerprints
lifecycle recovery/fencing
optional perceived ease/confidence
```

Do not convert human minutes to an arbitrary dollar value and do not emit a single ExHarness score.

## Frozen gate

The reducer returns:

```text
VALUE_DEMONSTRATED
NO_VALUE_DEMONSTRATED
INCONCLUSIVE
```

`VALUE_DEMONSTRATED` requires all of:

```text
quality:
  accepted units E >= D
  critical escaped defects = 0

human effort:
  total operatorActiveMs(E) <= 0.80 * total operatorActiveMs(D)

provider economics:
  providerCostPerAccepted(E) <= 1.10 * providerCostPerAccepted(D)

lifecycle:
  all 6 required scenarios pass
```

Lead time and paired effort distributions remain reported diagnostics rather than hidden in a composite.

Complete valid evidence with any primary gate failure => `NO_VALUE_DEMONSTRATED`.

Missing registered units, unknown primary cost, missing human-event coverage, task/verifier/profile drift or incomplete lifecycle evidence => `INCONCLUSIVE`.

Thresholds cannot be loosened after results.

## Research basis

- METR's 2025 experienced open-source developer RCT used real repository tasks and observed completion time, and found developer perceptions could diverge from measured time. BB-074 therefore uses observed active intervals rather than perceived speedup as the effort gate.
- METR's February 2026 experiment update warns that participation/selection effects can bias productivity experiments. BB-074 seals cohort membership before model results and retains all attempts.
- SPACE treats developer productivity as multidimensional rather than an activity count.
- Microsoft EngThrive combines Speed, Ease and Quality outcome measures, reinforcing a multidimensional product-value profile.
- DORA's delivery-performance model separates throughput from instability/recovery; BB-074 reports lead time and lifecycle recovery in addition to quality/economics.
- BB-077/081 provide the fixed-factor harness, measurement/failure contracts and supported Core-profile boundary reused here.
