# BB-063 — Durable ContextResolution identity, currentness and recovery

Status: **RESOLVED RESEARCH INPUT; no implementation authority**
Evidence checked: 2026-09-27
Trusted research baseline: f3b590217632fc4bf7430fb8f35a65fb989455ba

## Question

How should Oracle persist and reuse ContextResolution safely so a process restart, concurrent refresh, source drift or partial provider failure cannot turn stale/ambiguous context into current prompt input?

The solution must preserve BB-061 semantic identity and BB-062 source-authority/provider boundaries. Persistence is an optimization/evidence layer, never acceptance or product authority.

## Upstream contracts that are not reopened

BB-061 already defines requirementId, resolutionId, source snapshot/currentness validators, item provenance/itemDigest, materialization.id, COMPLETE/PARTIAL/UNSATISFIED and immutable progressive-step parent/index semantics.

BB-063 does **not** change resolutionId to include storage/backend details.

BB-062 already defines SourceCatalog, authoritative source-snapshot observations, provider/index snapshot identity, deterministic planning and the rule that indexed/derived providers cannot self-certify CURRENT.

BB-063 consumes those observations.

## Current ExHarness durability findings

### Existing manifest store

createJsonArtifactManifestStore already uses a useful publication pattern:

1. immutable digest-bound manifest bytes;
2. write to a unique temp file;
3. hard-link the complete temp file into the final no-overwrite publication slot;
4. concurrent same-semantic publication converges;
5. conflicting publication under the same accepted Backend identity fails closed;
6. read revalidates digest/content identity.

This avoids a mutable lock for manifest publication itself.

### Existing CAS-head store

createJsonCasHeadStore provides revision CAS with temp-write + rename, but serializes mutation through a filesystem *.lock created with open(..., "wx").

That pattern is valid for existing trusted single-host flows, but it is not the smallest fit for BB-063:

- a process can die after creating the lock and before cleanup;
- the leftover lock blocks later writers without a lease/recovery protocol;
- Oracle reuse does not need a mutable current-resolution pointer when current source observations are known first.

BB-063 therefore does not clone lockfile-head semantics into Oracle.

### Existing lineage store

createProductLineageStore demonstrates the useful split between immutable artifacts/history and currentness references. Oracle keeps the immutable-artifact lesson but can avoid a mutable current head entirely for cache reuse.

## Identity split selected

BB-061 semantic identity remains:

~~~text
ContextResolution.resolutionId
  = semantic result identity
~~~

BB-063 adds a separate durable reuse identity:

~~~text
ContextResolutionReuseKey
  = sha256(canonical({
      requirementId,
      resolverConfigDigest,
      sourceObservations,
      derivationInputs
    }))
~~~

The distinction is intentional:

- resolutionId says this semantic resolution is the same;
- reuseKey says this result was produced under the same authoritative source state and semantics-affecting resolver configuration, therefore it is eligible for reuse.

Two resolver implementations may produce the same resolutionId but have different reuseKey values after a semantic configuration change.

## SourceObservation v1

A durable source observation records the authoritative fence used for reuse:

~~~text
{
  observationId,
  evidenceId,
  source {
    kind,
    ref,
    mode: EXACT | CURRENT,
    requestedSnapshotRef?
  },
  observedState: PRESENT | ABSENT | UNAVAILABLE | AMBIGUOUS,
  observedSnapshotRef?,
  validators: [{ kind, value, strength: STRONG | WEAK }],
  authorityRef,
  authorityRevision,
  provenanceDigest?
}
~~~

Rules:

- PRESENT REQUIRED CURRENT must include an exact observedSnapshotRef and at least one STRONG validator;
- ABSENT is reusable only when the authority binds the negative observation to an authorityRevision/snapshot;
- UNAVAILABLE / AMBIGUOUS cannot authorize reusable REQUIRED context;
- EXACT binds the requested snapshot identity rather than following a newer repository/application head;
- observations are canonicalized by evidence order/source identity before hashing.

This preserves manifest-protected replay: an exact QA handoff can remain bound to its exact manifest/producers even when unrelated newer application state exists.

## ResolverConfiguration v1

Only semantics-affecting configuration enters durable reuse identity:

~~~text
{
  contractVersion,
  plannerRevision,
  materializationPolicyRevision,
  providerBindings: [
    {
      providerId,
      operationSetDigest,
      semanticConfigDigest
    }
  ]
}
~~~

Runtime timing, latency, worker id, retry count and provider-call cost are excluded.

Provider/index snapshots are not hidden inside config. They are explicit derivationInputs and must still be related to authoritative source observations.

## DerivationInput v1

Derived/index/graph context records inputs that affect output but are not themselves source authority:

~~~text
{
  providerId,
  operation,
  providerRevision,
  providerSnapshotRef?,
  configDigest
}
~~~

Examples include Zoekt-like index build identity, LSP adapter semantic revision, graph snapshot/version and structural-map ranking policy.

For CURRENT repository context, a providerSnapshotRef must be proven compatible with the authoritative repository SourceObservation. A stale index does not become current because it appears in derivationInputs.

## ContextResolutionReceipt v1

~~~text
{
  kind: CONTEXT_RESOLUTION_RECEIPT,
  version: 1,
  receiptId,
  reuseKey,
  requirementId,
  resolutionId,
  materializationId,
  resolutionArtifactRef,
  resolverConfigDigest,
  sourceObservations[],
  derivationInputs[],
  itemLineage: [
    {
      itemDigest,
      sourceObservationIds[],
      provenanceRefs[]
    }
  ]
}
~~~

receiptId hashes all semantic receipt fields except itself.

Every materialized item must have one lineage entry. A graph-derived item must still reach one or more authoritative source observations; graph/index identity alone is insufficient.

## Persistence selected

### Immutable artifacts

Persist exact canonical values in content-addressed files:

~~~text
objects/
  resolution-<sha256>.json
  receipt-<sha256>.json
~~~

Publication:

- write complete bytes to a unique temp file;
- sync/close the file;
- hard-link into the digest-derived final name with no overwrite;
- if final exists, verify exact content/digest and reuse;
- partial temp files never become canonical objects.

This follows the existing manifest-store pattern and the same broad content-addressed design used by Restic, Git and Bazel CAS.

### Exact reuse slots

~~~text
reuse/
  <reuseKey>.json
~~~

A reuse slot contains:

~~~text
{
  reuseKey,
  resolutionId,
  receiptRef
}
~~~

It is also published by temp-file + hard-link no-overwrite.

Concurrent semantics:

- same reuseKey + same resolutionId => converge on existing slot;
- same reuseKey + different resolutionId => NONDETERMINISTIC_RESOLUTION_CONFLICT and fail closed;
- no last-writer-wins current head exists.

Operationally different runs with the same semantic resolutionId may have different detailed receipts/cost counters; the first valid slot remains canonical reusable evidence.

## Why no mutable current head

Lookup always starts by observing source authority:

~~~text
observe authoritative sources
  -> compute reuseKey
  -> lookup exact reuse/<reuseKey>
~~~

If source state changes, the current reuseKey changes. Therefore a stale writer publishing the old key cannot make itself current for a later reader.

## Currentness fence at consumption

A cache key alone is insufficient because source state can change between lookup/materialization and prompt consumption.

Both cache-hit and fresh-resolution paths use a double observation fence:

~~~text
pre = observe()
key = reuseKey(pre)

lookup or resolve/materialize

post = observe()

if digest(post) != digest(pre):
  => STALE_DURING_RESOLUTION
  => do not publish/reuse/consume as current
~~~

BB-063 adds no unbounded retry. The caller receives explicit stale/currentness failure; later resolution may retry through normal bounded semantics.

## Reuse policy

### COMPLETE

Reusable only when requirement/config/reuseKey match, receipt/materialization digests validate, pre/post observations match, all item lineage closes over authoritative observations and the BB-061 resolution is consumable.

### PARTIAL

Reusable only when every unresolved OPTIONAL evidence entry has a strongly bound negative/absence observation. If absence/currentness cannot be fenced, PARTIAL may be returned for the live attempt but is not inserted into a reusable slot.

### UNSATISFIED

Never inserted into a reusable slot.

Failure/attempt artifacts may be retained for diagnostics separately, but failure caching is not a foundation feature.

## Selective invalidation

BB-063 does not delete old immutable history to make it invalid.

evaluateReceiptCurrentness(receipt, currentObservations) returns:

~~~text
{
  state: CURRENT | STALE,
  changedEvidenceIds[],
  reasons[]
}
~~~

A changed repository/artifact/source affects only receipts whose SourceObservations no longer match. Old receipts remain historical evidence. Garbage collection/retention is separate maintenance work.

## Manifest compatibility

For application-artifact context:

1. existing createManifestArtifactReader still validates exact manifest, producer revision, acceptance decision, stored revision and content digest;
2. Oracle receives the already validated source read;
3. SourceObservation binds the exact manifest ref/digest and relevant entry identity;
4. item lineage records manifest/provenance refs;
5. the durable receipt cannot substitute for or weaken manifest validation.

A receipt with matching artifact bytes but wrong producer/revision/acceptance provenance is invalid.

## Failure-model experiment

A disposable filesystem model tested the selected immutable-slot semantics.

### Same key, same result

20 concurrent publications of the same reuseKey + semantic receipt produced one canonical reuse slot; one writer published and the rest converged as reused.

### Same key, different semantic result

Publishing a different resolutionId under the same reuseKey produced a conflict instead of last-writer-wins.

### Crash after materialization, before reuse publication

The immutable blob remained orphaned but harmless. On retry the slot was absent, the same blob could be reused and publication completed.

### Source change

Repository observations A and B produced different reuse keys. Lookup under B could not return the A slot.

### Source change during materialization

Pre-observation A and post-observation B differed, so publication/current consumption was rejected.

### Stale writer

Even if a stale writer later writes an old-key historical slot, readers that observe B query only B's key. The Worker rule is stronger: pre/post drift forbids publication.

### Partial provider failure

No reusable slot is published for unresolved REQUIRED context.

### Lockfile comparison

A simulated crash leaving a *.lock file caused the next exclusive-lock writer to fail immediately. This is why BB-063 does not introduce a mutable lockfile cache head.

## Worker scope handoff

BB-063 Worker implements:

- strict SourceObservation / ResolverConfiguration / DerivationInput / ContextResolutionReceipt;
- canonical reuseKey / receiptId helpers;
- immutable content-addressed resolution/receipt store;
- atomic no-overwrite reuse slots;
- double-observation currentness fence;
- currentness evaluator with selective changed-evidence reasons;
- durable reuse/replay coordinator;
- manifest-protected compatibility tests;
- crash/concurrency/failure fixtures.

It must not add:

- a mutable current resolution head;
- lockfile-based cache ownership;
- SQLite/Graphiti/Cognee runtime dependency;
- automatic unbounded refresh/retry;
- durable model conversation memory;
- Application acceptance/publication/recovery authority;
- garbage collection as correctness logic.

## Handoff

BB-063 can become READY when the implementation plan encodes the exact durable contracts, no-head reuse algorithm, currentness fence, manifest compatibility and failure-injection verification above. BB-064 then accepts the complete Oracle foundation end to end.
