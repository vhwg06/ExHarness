# BB-061 — ContextRequirement / ContextResolution semantic contract

Status: **RESOLVED RESEARCH INPUT; no implementation authority**
Evidence checked: 2026-09-27
ExHarness trusted baseline: `d1019fd1e92d2a8b14e3eb1316b720c53deecb4a`

## Question

What is the smallest source-agnostic contract that lets Core request bounded semantic context from Oracle, preserves exact provenance/currentness, supports explicit progressive resolution, and does not expose provider commands or domain authority?

## Current-source findings

### F1 — Current Application contracts already contain two useful compatibility cases

Backend currently binds:

```text
BackendWorkOrder
  repositoryRef
  revision
  requiredFiles[]
        |
        v
BackendContext
  repository { ref, revision }
  files[] { path, content, sourceRef }
```

The Backend worker then requires the resolved repository ref/revision and file ordering to exactly match the work order.

QA currently binds:

```text
QaWorkOrder
  upstream { workOrderId, revision, acceptanceDecision }
  requiredArtifacts[]
        |
        v
QaContext
  upstream
  artifacts[] {
    ref, path?, content, sourceRef,
    provenance {
      sourceClass = APPLICATION_ARTIFACT,
      producerWorkOrderId,
      acceptanceDecision
    }
  }
```

These are compatibility examples for exact source constraints and provenance. They are not the final caller-facing Oracle API.

### F2 — Core has a prompt projection boundary but no source-resolution boundary

`renderAgentContext(...)` already owns:

- selected context blocks;
- trusted/untrusted prompt metadata;
- history projection/reduction;
- `maxBlocks`;
- `maxHistoryEvents`;
- `maxSerializedChars`.

`AgentRuntime` renders context before model generation. A turn-aware strategy calls `prepareTurn()` before each model turn.

Therefore the new resolution seam should run **before** ordinary prompt rendering and project its result into ordinary fixed context blocks. The existing prompt-size enforcement remains authoritative.

### F3 — Resolution must not be a capability/tool call

Capability, Resource and LiveObject calls are action surfaces exposed to strategy/model behavior. Required context grounding must be deterministic harness-side work, not an optional model action.

### F4 — A shared sibling contracts package is not earned

A new `@exharness/context-contracts` package would create another cross-workspace dependency. Current CI runs source directly without `npm install`, while the Core package is independently checked with `npm pack --dry-run`.

BB-061 therefore keeps the **semantic schema implementation under `@exharness/oracle`**. Core receives opaque JSON-safe requirement/resolution values through an injected resolver port and never imports Oracle.

## Contract selected

### ContextRequirement v1

Canonical semantic shape:

```text
{
  kind: "CONTEXT_REQUIREMENT",
  version: 1,
  requirementId: sha256(canonical(semantic fields below)),

  consumerRef: string,
  semanticNeed: string,

  evidence: [
    {
      id: string,
      necessity: "REQUIRED" | "OPTIONAL",
      need: string,
      source: {
        kind: string,
        ref: string,
        snapshot:
          { mode: "EXACT", ref: string }
        | { mode: "CURRENT" },
        itemRefs?: string[]
      }
    }
  ],

  budget: {
    maxItems: positive integer,
    maxMaterializedBytes: positive integer,
    maxProviderCalls: positive integer,
    maxResolutionSteps: positive integer
  }
}
```

Rules:

- `requirementId` hashes every semantic field except itself.
- Evidence IDs are unique and order is semantic; callers cannot silently reorder required evidence without changing identity.
- `consumerRef` scopes the requirement to its semantic consumer but grants no authority.
- `semanticNeed` and per-evidence `need` describe WHAT is needed.
- `source.kind/ref/snapshot/itemRefs` constrain source identity, not HOW a provider searches.
- Provider/tool fields such as `providerId`, `tool`, `operation`, `queryDsl`, `mcpMethod` are not contract fields and are rejected by strict parsing.
- An EXACT source must name the exact source snapshot. CURRENT means Oracle must bind the result to an exact snapshot and strong currentness evidence before consumption.
- Empty evidence is invalid.
- No timestamps are required for semantic identity.

Examples:

Backend exact-file requirement:

```text
consumerRef = BackendWorkOrder.id
semanticNeed = BackendWorkOrder.task
evidence[i]:
  necessity = REQUIRED
  source.kind = REPOSITORY
  source.ref = repositoryRef
  source.snapshot = EXACT(revision)
  source.itemRefs = [requiredFile]
```

QA accepted-artifact requirement:

```text
consumerRef = QaWorkOrder.id
semanticNeed = QaWorkOrder.task
evidence[i]:
  necessity = REQUIRED
  source.kind = APPLICATION_ARTIFACT
  source.ref = artifact.ref
  source.snapshot = EXACT(upstream.revision)
  source.itemRefs = artifact.path? [path] : []
```

The producer work-order and acceptance-decision evidence are resolution provenance, not provider commands.

Semantic-code / lexical / graph providers can all satisfy a semantic requirement because the caller constrains source identity and semantic need without naming the retrieval implementation. For example, a repository `CURRENT` requirement can be fulfilled by lexical search, symbol/LSP retrieval, graph-assisted retrieval or a composition of those below Oracle.

## ContextResolution v1

Canonical semantic shape:

```text
{
  kind: "CONTEXT_RESOLUTION",
  version: 1,
  resolutionId: sha256(canonical(semantic resolution identity)),
  requirementId: string,

  step: {
    index: non-negative integer,
    previousResolutionId: string | null
  },

  status: "COMPLETE" | "PARTIAL" | "UNSATISFIED",

  items: [
    {
      evidenceId: string,
      rank: non-negative integer,
      source: {
        kind: string,
        ref: string,
        snapshotRef: string,
        itemRef: string | null
      },
      currentness: {
        validators: [
          {
            kind: "REVISION" | "CONTENT_DIGEST" | "OPAQUE",
            value: string,
            strength: "STRONG" | "WEAK"
          }
        ]
      },
      provenance: [
        {
          kind: string,
          ref: string,
          digest?: string
        }
      ],
      content: JSON-safe value,
      itemDigest: sha256(canonical(source + currentness + provenance + content))
    }
  ],

  unresolved: [
    {
      evidenceId: string,
      reason:
        "MISSING"
        | "STALE"
        | "AMBIGUOUS"
        | "BUDGET_EXHAUSTED"
        | "SOURCE_FAILURE"
        | "UNSUPPORTED"
        | "CURRENTNESS_UNVERIFIABLE"
        | "DEFERRED"
    }
  ],

  materialization: {
    id: sha256(canonical(ordered items)),
    bytes: UTF-8 bytes of canonical(ordered items)
  },

  consumed: {
    items: integer,
    materializedBytes: integer,
    providerCalls: integer,
    resolutionSteps: integer
  }
}
```

Rules:

- `materialization.id` binds the exact ordered resolved items.
- `resolutionId` binds `requirementId + step + status + materialization.id + unresolved`.
- Operational cost counters in `consumed` are evidence but are **not** part of resolution identity. A cheaper provider implementation can yield the same semantic resolution.
- Each `itemDigest` binds source snapshot, currentness validators, provenance and content.
- Every item references a declared evidence ID.
- Every evidence ID is either represented by one or more items or by one explicit unresolved entry.
- Ranks are contiguous within each evidence ID after normalization.
- `consumed` is cumulative for the resolution chain and cannot exceed the requirement budget.
- `materialization.bytes` must equal the deterministic UTF-8 byte count of canonical ordered items.

Status:

- `COMPLETE`: all REQUIRED and OPTIONAL evidence requirements are satisfied.
- `PARTIAL`: every REQUIRED requirement is satisfied, but one or more OPTIONAL requirements are unresolved/deferred.
- `UNSATISFIED`: at least one REQUIRED requirement is unresolved. It is not consumable as prompt context.

This distinguishes an explicit partial optional result from a hidden missing required source.

## Currentness semantics

Currentness is a validation relation, not a timestamp.

RFC 9110 distinguishes weak and strong validators. Strict revision control and collision-resistant hashes are examples of strong representation validators; modification time can be weak. ExHarness adopts that separation:

- `lastModified`/time metadata may be provider evidence but is not sufficient by itself for a REQUIRED CURRENT resolution.
- REQUIRED CURRENT source evidence must resolve to an exact `snapshotRef` and at least one strong validator.
- EXACT requirements preserve their requested snapshot identity and still bind content with `itemDigest`.
- A stale or unverifiable required source produces `UNSATISFIED`, never a current item.
- Semantic correctness/acceptance is not implied by currentness. A strong digest proves identity, not truth.

BB-063 owns durable storage, cache validity and replay/invalidation machinery. BB-061 defines the identity that BB-063 must preserve.

## Provenance semantics

`provenance[]` is an ordered set of typed refs, not application authority.

For QA accepted-artifact compatibility, the mapper records at least:

```text
{ kind: "PRODUCER_WORK_ORDER", ref: upstream.workOrderId }
{ kind: "ACCEPTANCE_DECISION", ref: decision.id, digest: decision.digest }
```

A manifest-protected read may additionally record:

```text
{ kind: "ARTIFACT_MANIFEST", ref: manifestRef, digest: manifestDigest }
```

These entries establish lineage/currentness inputs. They do not allow Oracle to accept, publish or recover product state.

## Budget semantics

The requirement budget is hard and deterministic:

- `maxItems`: maximum normalized resolved items;
- `maxMaterializedBytes`: maximum UTF-8 canonical bytes of normalized items;
- `maxProviderCalls`: maximum provider invocations;
- `maxResolutionSteps`: maximum immutable resolution steps.

Oracle must reserve/check the applicable counter before exceeding it. If a REQUIRED evidence need cannot be satisfied inside the budget, status is `UNSATISFIED` with `BUDGET_EXHAUSTED`. Optional work may produce `PARTIAL`.

Token budget is deliberately **not** a v1 semantic field. Tokenization is model/adapter-specific and Core already enforces a separate prompt serialization limit. A later context-budget phase may map byte/materialization budget into model-specific token policy without changing source identity.

## Progressive resolution

Progression is explicit, immutable and bounded:

- first resolution: `step.index = 0`, `previousResolutionId = null`;
- next step: exact previous resolution ID and `index = previous.index + 1`;
- cumulative consumption never decreases;
- every step has a complete item/unresolved snapshot and a new `resolutionId`;
- consumers never observe a resolution mutating in place;
- no step may exceed the original requirement budget.

**BB-061 runtime behavior resolves once per AgentRuntime call.** It does not automatically request later steps. Progressive re-resolution is a future runtime feature. The v1 chain fields ensure that later work cannot introduce hidden context growth or overwrite earlier resolution identity.

## Core runtime seam

BB-061 adds a generic Core-side pre-render abstraction without an Oracle dependency:

```text
createAgentRuntime({
  contextBlocks,
  contextRequirementBlocks,
  contextResolver
})
```

A requirement block contains:

```text
{
  name,
  description?,
  trust,
  requirement,         // opaque JSON-safe value to Core
  project(resolution, metadata) -> JSON-safe prompt value
}
```

The injected resolver supplies:

```text
resolve(requirement, metadata) -> resolution
```

Core behavior:

1. resolve the ordinary context selection;
2. identify selected requirement-block names;
3. before strategy/model execution, call the resolver exactly once per selected requirement block;
4. call the block's `project` function;
5. turn the projected value into an ordinary fixed context block preserving name/description/trust;
6. pass ordinary + projected fixed blocks into existing `renderAgentContext`;
7. reuse the same fixed projected blocks across all turns of one agent call.

The Core module validates JSON-safe cloneability but does not import or interpret the Oracle schema.

Failure behavior:

- selected requirement block + no resolver => fail before model generation;
- resolver rejection => fail before prompt projection/model generation;
- project rejection, including an Oracle `UNSATISFIED` result => fail before model generation;
- unselected requirement block => no resolver call;
- no Capability/Resource/LiveObject invocation is involved;
- ordinary fixed/dynamic context blocks continue unchanged.

This is a **pre-prompt context-resolution port**, not a model-visible tool.

## External evidence

- RFC 9110 §8.8: strong vs weak validators; strict revision and collision-resistant representation hashes are suitable strong validators. Use this as a currentness analogy, not as an Oracle protocol.
- Bazel remote caching: actions declare inputs; action cache identity and CAS content identity are distinct. Use this as evidence for separating requirement identity from materialization/content identity.
- MCP 2026-07-28 keeps `resources/read` separate from tool invocation and adds explicit `ttlMs` / `cacheScope` cache hints to list/resource-read results. Use this as evidence for resource-read/freshness metadata separation; cache freshness hints are not strong representation validators for ExHarness REQUIRED currentness.
- Graphiti/Zep temporal facts expose validity intervals and source-derived graph facts. Use this as evidence that temporal validity belongs in context systems; it does not make graph-derived facts authoritative product truth.
- Aider repo-map remains evidence for bounded projection; token budgeting stays above the source identity contract.

## Falsifiable worker checks

The plan is implementation-ready only if tests can prove:

- canonical hash changes for every semantic requirement field and ignores only its own derived ID;
- resolution/materialization IDs are deterministic and exclude provider cost/timing;
- required missing/stale/ambiguous/currentness-unverifiable/budget-exhausted -> UNSATISFIED;
- optional unresolved -> PARTIAL, not silent COMPLETE;
- strong currentness is required for CURRENT required sources;
- provenance changes alter item/materialization/resolution identity;
- budget counters cannot exceed original requirement;
- progressive chain index/parent/cumulative counters are monotonic;
- provider/tool fields are rejected by strict requirement parsing;
- Core requirement resolution executes once per selected block per call and zero times for unselected blocks;
- turn-aware multiple turns reuse the same resolution;
- resolver/project failure causes zero model calls;
- existing ordinary context-block tests remain unchanged;
- Core has no Oracle import;
- Backend/QA compatibility fixtures preserve current shapes.
