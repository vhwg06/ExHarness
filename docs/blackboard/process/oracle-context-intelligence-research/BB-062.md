# BB-062 — Oracle source-provider topology and semantic code retrieval

Status: **RESOLVED RESEARCH INPUT; no implementation authority**
Evidence checked: 2026-09-27
Trusted research baseline: `eafc1e5af25b1bfa681d4ed730bba387a8e5c7d8`

## Question

What is the smallest provider topology that lets Oracle add exact repository/artifact reads, indexed lexical search, semantic-code lookup, structural context and future graph/external sources without expanding the caller-facing ContextRequirement contract or turning providers into model-visible tools?

## Retained upstream contracts

BB-060 selected Oracle as infrastructure-owned context resolution with no Core import of Oracle and no default Capability/Resource/LiveObject seam.

BB-061 selected:

- strict provider-neutral ContextRequirement;
- exact ContextResolution identity/currentness/provenance/budget semantics;
- an injected Core pre-render resolver port;
- once-per-agent-call context resolution;
- provider/tool commands forbidden from the caller-facing requirement.

BB-062 therefore works **below** ContextRequirement/ContextResolution. It must not redesign those contracts.

## Current-source findings

Current source still has only two direct source loops in `packages/agentic-system/src/oracle.js`:

1. exact repository file read by repositoryRef + revision + path;
2. exact accepted application-artifact read with producer/revision/acceptance provenance.

There is no current provider registry, semantic-code provider, indexed lexical provider, graph provider, source catalog or retrieval planner.

The current two loops remain compatibility cases and future exact-source providers; they are not enough for semantic runtime retrieval.

## Research experiment A — bounded code-retrieval family shootout

A disposable research-only experiment was run over the current `main` snapshot using the same 8-file corpus and predeclared relevant files.

Corpus:

- `packages/core-harness/src/context.js`
- `packages/core-harness/src/agent-runtime.js`
- `packages/agentic-system/src/oracle.js`
- `packages/agentic-system/src/artifact-manifest.js`
- `packages/agentic-system/src/durable-backend-qa.js`
- `packages/core-harness/src/effect-reconciliation.js`
- `scripts/blackboard-jev.mjs`
- `scripts/blackboard-delivery-contract.mjs`

Total materialized corpus: **172,904 bytes**.

Four predeclared queries covered:

1. bounded prompt context before model generation;
2. QA artifact provenance / manifest integrity;
3. effect reconciliation / non-reconcilable replay;
4. bounded objective-scoped JEV research evidence.

Research implementations were deliberately family-level approximations rather than claims that the external binaries were executed:

- **lexical** — text/trigram-like weighted retrieval, representing the Zoekt family;
- **symbol** — symbol-definition/query overlap, representing LSP/Serena-style semantic retrieval;
- **structural** — symbol reference graph propagation, representing Aider repo-map style structural ranking.

Aggregate top-3 results:

| Family | mean Recall@3 | mean Precision@3 | mean MRR | mean bytes@3 |
|---|---:|---:|---:|---:|
| lexical | 0.792 | 0.500 | 0.875 | 87,713 |
| symbol | **0.875** | **0.583** | **0.875** | 79,754 |
| structural | 0.750 | 0.500 | 0.813 | 77,942 |
| typed graph/context | **1.000** | **0.667** | **1.000** | **70,163** |

Important per-query findings:

- symbol retrieval recovered both Core prompt-context files where lexical missed one;
- symbol + structural both exactly recovered the three QA artifact/provenance files;
- lexical was already sufficient for the isolated effect-reconciliation query;
- structural recovered the JEV materializer + delivery-contract pair, but failed the prompt-context query when graph propagation over-weighted unrelated central files.

### Typed graph/context arm on the same Q1–Q4 problems

To close the same-problem comparison, a fourth disposable arm used the **same 8 files, the same four queries and the same predeclared relevant-file sets**.

The graph was manually normalized from current source/import/contract relations rather than produced by Graphiti/Cognee:

- `agent-runtime.js -> context.js` through the verified `renderAgentContext` import;
- `durable-backend-qa.js <-> artifact-manifest.js <-> oracle.js` through manifest-protected QA/source-resolution relations;
- `blackboard-jev.mjs -> blackboard-delivery-contract.mjs` through its verified delivery-contract import;
- isolated effect-reconciliation semantics remain a single authoritative node.

Nodes carry bounded semantic labels derived from current source responsibility; edges carry typed relation labels. Ranking uses query-to-node/relation overlap plus one-hop relation evidence.

On Q1–Q4 this arm produced:

- mean Recall@3 = **1.000**;
- mean Precision@3 = **0.667**;
- mean MRR = **1.000**;
- mean materialized bytes@3 = **70,163**.

This is evidence for a typed graph/context **provider/projection family** on the same retrieval problems. It is **not** evidence that Graphiti, Cognee or any external graph database was executed or should be adopted.

### Interpretation

The experiment does **not** justify one universal retriever.

- indexed lexical search remains a cheap/high-recall baseline;
- semantic symbol/reference retrieval adds measurable value and should be a first-class provider capability;
- structural ranking can reduce context but is fragile as a primary retriever; it belongs above normalized symbol/reference edges as a bounded projection/ranking technique;
- typed graph/context projection performed strongly when authoritative relations were explicit, but this does not justify a graph database;
- planner composition should use complementary providers rather than forcing one family to answer every need.

## Research experiment B — graph feasibility

A second disposable experiment used current authoritative structured edges from:

- `docs/blackboard/component-registry.json` — 12,516 bytes;
- `docs/blackboard/work-graph.json` — 79,191 bytes.

Queries asked for exact ownership/source/dependency projections such as:

- Oracle infrastructure current Living refs, source roots and contract refs;
- Core context-resolution ownership;
- BB-061 routing + direct dependency;
- BB-064 foundation dependency closure.

Direct typed projection returned exact answers averaging **399 bytes** versus **48,983 raw bytes**, a mean reduction of **97.71%**.

### Interpretation

This proves value for a **graph/provider seam and typed relation projection**.

It does **not** prove value for a separate temporal graph database in the foundation. Current authoritative structured edges already answer these bounded questions exactly. A graph database should be adopted only when later experiments demonstrate value for relationships/currentness that cannot be maintained as explicit authoritative edges.

## External evidence and reuse decision

All public GitHub examples below satisfy the standing >=1,000-star rule at the 2026-09-27 check.

### Zoekt — adopt as lexical adapter target

Pinned source: `sourcegraph/zoekt@153817f643cde8b229ee388c1dddbcf07f4798af`
License: Apache-2.0.

Primary-source findings:

- trigram-indexed substring/regexp source search;
- symbol-aware ranking;
- local command, JSON API and gRPC surfaces;
- indexserver can periodically fetch/reindex;
- repository branch metadata carries exact versions/commits.

Decision:

- **ADAPTER TARGET** for indexed lexical retrieval;
- do not embed Zoekt implementation into Oracle;
- Oracle adapter must bind results to repository/version metadata and reject a result that cannot prove the required snapshot/currentness;
- transport is injected; HTTP/JSON is the smallest first external transport because it avoids linking Go into the Node package.

### Serena / SolidLSP — reuse semantic capability, reject full application dependency

Pinned source: `oraios/serena@7a2968335f2198b966864de1ce3655c8e485a653`
License:
- Serena application: GPL-3.0-or-later;
- SolidLSP: MIT.

Primary-source findings:

- symbol lookup, outline, references, declaration and implementation queries;
- LSP backend supports many languages;
- Serena exposes these as agent/MCP tools;
- SolidLSP is separately reusable MIT infrastructure.

Decision:

- **DO NOT depend on the full Serena application** in ExHarness foundation;
- define a semantic-code provider over a small injected `symbolClient` contract;
- LSP/SolidLSP can back that client out-of-process later;
- MCP/Serena's model-visible tool surface must not leak into ContextRequirement or planner semantics.

### Aider repo-map — inspiration-only structural projection

Pinned source: `Aider-AI/aider@5dc9490bb35f9729ef2c95d00a19ccd30c26339c`
License: Apache-2.0.

Primary-source findings:

- codebase map from definitions/references;
- dependency graph ranking / PageRank;
- explicit token budget;
- map refresh can be controlled to reduce recomputation.

Decision:

- **INSPIRATION / ALGORITHM REUSE**, not application dependency;
- structural projection should consume normalized symbol/reference edges from providers and fit a bounded context budget;
- do not make structural PageRank the primary retriever because the research family benchmark showed a real failure mode on the Core prompt-context query.

### Graphiti — defer backend adoption

Pinned source: `getzep/graphiti@ba4a9cb32495b6864160616f8dfa2b898f4a500c`
License: Apache-2.0.

Primary-source findings:

- incremental graph updates;
- bi-temporal modeling;
- valid_at / invalid_at range queries;
- graph grouping/storage and MCP surface.

Decision:

- **DEFER / PROVIDER SEAM ONLY**;
- its temporal model is useful design evidence for future Context Graph/currentness work;
- BB-062 does not add Graphiti persistence because the current typed-edge experiment already answers foundation cross-source queries with exact provenance and ~97.7% materialization reduction.

### Cognee — reject as foundation source-truth dependency

Pinned source: `topoteretes/cognee@eb90d03740755f5252b8b12cce91fd09970f2d81`
License: Apache-2.0.

Primary-source findings:

- persistent AI memory;
- graph/vector/code context;
- code graph of symbols/dependencies;
- automatic/chosen retrieval strategy routing;
- session distillation and memory improvement lifecycle.

Decision:

- **REJECT AS FOUNDATION DEPENDENCY**;
- useful future comparison for graph/code retrieval;
- memory/session/improvement semantics exceed Oracle's source-truth boundary and risk conflating remembered context with authoritative source/currentness.

## Selected provider topology

```text
ContextRequirement
        |
        v
Oracle RetrievalPlanner            deterministic in BB-062
        |
        +---- SourceCatalog
        |       explicit composition-time registrations
        |       no model-visible generic tool registry
        |
        +---- exact repository provider        [from BB-060]
        +---- exact application-artifact provider [from BB-060]
        +---- lexical provider                 [Zoekt adapter target]
        +---- semantic-code provider           [symbolClient / LSP seam]
        +---- structural projection            [Aider-inspired, normalized edges]
        +---- context-graph provider seam       [typed graph client; no DB selected]
        +---- external provider seam            [transport adapter; MCP optional]
        |
        v
ProviderCandidate[]
        |
        v
BB-061 ContextResolution materialization/validation
```

## Provider capability model

Provider registration is explicit at composition time.

A descriptor contains only Oracle-internal capability metadata:

```text
{
  providerId,
  sourceKinds[],
  operations[],
  snapshotModes[],
  currentnessValidators[],
  maxConcurrentCalls,
  costClass
}
```

Operations are bounded Oracle-internal verbs:

```text
READ_EXACT
SEARCH_LEXICAL
LOOKUP_SYMBOL
FIND_REFERENCES
STRUCTURAL_MAP
TRAVERSE_GRAPH
FETCH_EXTERNAL
```

Rules:

- providerId/operation never enter ContextRequirement;
- duplicate providerId fails closed;
- a provider cannot claim work lifecycle, acceptance, publication, recovery or effect authority;
- provider registration does not grant the model a tool;
- provider outputs are normalized before ContextResolution materialization.

## Provider candidate contract

Each provider returns bounded candidates:

```text
{
  evidenceId,
  source {
    kind,
    ref,
    snapshotRef,
    itemRef
  },
  validators[],
  provenance[],
  content,
  providerEvidence {
    providerId,
    operation,
    score?,
    rank?,
    elapsedMs?
  }
}
```

`providerEvidence` is diagnostic/ranking evidence only. It is not semantic source identity and cannot certify currentness.

A provider may return no candidates plus a typed provider failure. Oracle converts unresolved required evidence through BB-061 failure semantics.

## Retrieval planner

The first RetrievalPlanner is **deterministic**.

Input:

```text
ContextRequirement + SourceCatalog + remaining budget
```

Output:

```text
RetrievalWork[] {
  evidenceId,
  providerId,
  operation,
  sourceConstraint,
  semanticNeed,
  reservedBudget
}
```

Rules:

- planner work is context-local retrieval, not Application scheduling;
- budget is reserved before provider invocation;
- exact itemRefs prefer READ_EXACT;
- repository semantic needs without exact items may use lexical + semantic providers within budget;
- structural projection consumes existing symbol/reference candidates and cannot initiate unbounded source discovery;
- graph traversal is used only when the requirement/source constraints need explicit relation paths;
- fallback cannot weaken EXACT/CURRENT/currentness requirements;
- provider failures can move to another compatible provider only when the same source/currentness contract can still be proven.

### Why not model-assisted planner now?

A planner model would add:

- another paid/model turn before context is available;
- nondeterministic provider selection;
- cache/prompt sensitivity;
- harder attribution of retrieval cost and failure;
- a new way for source/tool details to leak into model behavior.

Current family results do not establish that this cost is necessary. Model-assisted planning remains a later benchmark arm, not BB-062 foundation behavior.

## External / MCP source rule

MCP is transport, not source identity.

A future MCP-backed provider must:

1. map remote resource/capability output into the ProviderCandidate contract;
2. bind exact source ref/snapshot/currentness validators;
3. preserve provenance;
4. obey Oracle budget/failure rules;
5. expose no MCP task/session/tool authority above the provider seam.

An MCP response lacking sufficient source/currentness evidence cannot satisfy REQUIRED context.

## Failure and currentness rules

- stale index => provider failure / unresolved STALE; never silently return as CURRENT;
- unsupported language => semantic provider UNSUPPORTED; lexical may still be used if source/currentness constraints remain satisfied;
- deleted/renamed symbol => explicit missing or lexical fallback, not fabricated symbol identity;
- ambiguous symbol => AMBIGUOUS unless planner has a bounded disambiguation rule;
- graph fact without authoritative source path => cannot satisfy required source truth;
- external transport success without source validator => CURRENTNESS_UNVERIFIABLE;
- provider timeout/call failure consumes reserved call budget and is recorded; retries require explicit planner policy.

## Worker scope handoff

BB-062 worker should implement only the smallest provider/planner foundation:

- SourceCatalog + descriptor validation;
- deterministic RetrievalPlanner;
- normalized ProviderCandidate contract;
- exact-provider registration of BB-060 outputs;
- injected lexical client adapter shaped for Zoekt-like search results;
- injected semantic symbol client adapter shaped for LSP/SolidLSP-like operations;
- Aider-inspired structural projector over normalized symbol/reference edges;
- graph provider/client seam without Graphiti/Cognee persistence;
- external transport seam without an MCP lifecycle;
- deterministic benchmark fixture preserving the predeclared queries/ground truth above.

It must **not** add:

- a provider-selection LLM;
- Graphiti/Cognee storage;
- a generic agent tool registry;
- automatic background indexing lifecycle;
- durable resolution cache/replay (BB-063);
- post-foundation Context Graph runtime (later Oracle efficiency continuation).

## Handoff

BB-062 can become READY when the implementation plan encodes this exact topology, reuse decisions, deterministic planner rules, currentness/failure guards and benchmark/negative tests. BB-063 then owns durable ContextResolution storage/currentness invalidation/replay.
