## Acceptance question

What exactly must be true before the rebound Oracle phase is allowed to leave Research/SA as a coherent Context Intelligence foundation, and how do we hand its efficiency claims into the repository's reset harness-benchmark program without claiming product value from deterministic prototypes?

BB-064 is not another architecture-design task. It consumes BB-060..063 and closes only the smallest end-to-end foundation.

## Convergence of BB-060..063

### BB-060 — physical ownership and runtime boundary

Selected facts:

- Oracle is infrastructure-owned, not Application-owned;
- existing Backend repository and QA accepted-artifact reads become compatibility providers below Oracle;
- Core does not import Oracle implementation;
- Oracle is not a Capability, Resource, LiveObject or model-visible tool;
- runtime resolution is injected before Core prompt projection.

### BB-061 — semantic contract and Core port

Selected facts:

- caller-facing ContextRequirement is provider-neutral and strict;
- ContextResolution has deterministic semantic identity, source/currentness/provenance, explicit unresolved state and hard materialization/provider-call/step budgets;
- Core receives opaque JSON-safe requirement/resolution values through an injected pre-render resolver port;
- requirement blocks resolve once per AgentRuntime call and remain frozen across turns;
- progressive chain identity exists, but automatic progressive re-resolution is not delivered in the foundation.

### BB-062 — provider topology and deterministic planner

Selected facts:

- SourceCatalog/provider metadata remains Oracle-internal;
- caller requirements never contain provider/tool/MCP commands;
- exact, lexical, semantic-code, structural, graph and external seams normalize to ProviderCandidate;
- indexed/derived providers cannot self-certify CURRENT;
- deterministic RetrievalPlanner reserves budget and composes providers;
- graph is a typed provider/projection seam only; Graphiti/Cognee persistence is not selected;
- model-assisted planner selection is not delivered.

### BB-063 — durable reuse and recovery

Selected facts:

- BB-061 resolutionId remains semantic result identity;
- durable reuseKey separately binds requirement + semantics-affecting resolver configuration + authoritative source observations + derivation inputs;
- immutable resolution/receipt objects plus exact no-overwrite reuse slots replace a mutable current-cache head;
- cache hit and fresh resolution both require authoritative pre/post observation equality before current consumption/publication;
- historical receipts are retained; currentness invalidation is logical/selective;
- persistence cannot weaken manifest-protected Backend→QA artifact validation.

## Smallest foundation composition seam

BB-064 Worker should add one composition facade under Oracle:

~~~text
createOracleContextResolver({
  sourceCatalog,
  retrievalPlanner,
  durability?,
  resolverConfiguration
})
  .resolve(contextRequirement, metadata?)
      -> ContextResolution
~~~

The facade composes delivered dependency outputs only:

~~~text
ContextRequirement
  -> parse/identity             [BB-061]
  -> authoritative pre-observe [BB-062]
  -> durable exact-key lookup   [BB-063, optional]
  -> deterministic plan         [BB-062]
  -> provider execution         [BB-060/062]
  -> candidate normalization    [BB-062]
  -> materialize/validate       [BB-061]
  -> authoritative post-observe[BB-062]
  -> receipt/reuse publication  [BB-063, optional]
  -> ContextResolution
~~~

The facade does not:

- import Application contracts;
- expose provider operations to Core/model;
- own work scheduling or acceptance;
- add a second semantic contract;
- add a model turn;
- silently retry currentness drift;
- add graph/database/session memory.

Core receives this facade through the already researched injected contextResolver port.

## Research conclusion

The foundation is coherent and implementation-ready as a bounded composition layer:

- physical Oracle ownership is clear;
- semantic identity is provider-neutral;
- planner/provider internals stay below the caller contract;
- currentness is authoritative, not self-reported by indexes;
- durable reuse is separately fenced from semantic resolution identity;
- Core uses a generic pre-render resolver;
- deterministic failure classes are explicit;
- benchmark claims are deferred to a fixed-factor program.

BB-064 can become READY when its worker plan encodes the dependency-convergence gate, one Oracle composition facade, actual-delivery foundation probe, negative matrix, benchmark handoff and continuation boundary above.
