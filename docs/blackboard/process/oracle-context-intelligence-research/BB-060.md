# BB-060 — Oracle runtime architecture and physical ownership

Status: **RESOLVED RESEARCH INPUT; no implementation authority**
Evidence checked: 2026-09-26
ExHarness baseline: `32de91cc5315953befd3ca82149be7bdb2fb2b9e`

## Question

What is the smallest physical and runtime architecture that lets Oracle become the infrastructure-owned Context Intelligence Plane without freezing the old two-reader shape as the final contract or moving Application authority/provider policy into Core?

## Current-source findings

### F1 — Oracle is still Application-owned source code

`packages/agentic-system/src/oracle.js` owns both current source loops and imports Application schemas directly. `prepareBackendObjective()` and `runQaObjective()` call those resolvers before invoking the Backend/QA worker.

Current path:

```text
Application objective
  -> Application WorkOrder
  -> packages/agentic-system/src/oracle.js
  -> repositoryReader / artifactReader
  -> Application context schema
  -> Worker
```

The previous physical-ownership finding is therefore still valid.

### F2 — Core already owns bounded prompt-context rendering, not source resolution

`packages/core-harness/src/context.js` provides selected context blocks, dynamic block resolution, history reduction and hard serialized-size limits. `AgentRuntime` renders those blocks before or during strategy turns.

However a dynamic block receives only runtime metadata (`callId`, judgment and turn). It does not represent a durable source resolution with independent requirement identity, provenance/currentness or materialization identity.

Therefore **Oracle should not be collapsed into a dynamic context block**. Context blocks are the projection/rendering layer that consumes a resolution.

### F3 — Capability/resource integration is the wrong default seam

`AgentRuntime.invoke()`, Resource and LiveObject surfaces are model/strategy-visible action mechanisms. Using them as the primary Oracle resolution path would:

- make source discovery/retrieval policy part of the agent tool surface;
- spend model turns/tool calls merely to obtain baseline context;
- let model behavior decide whether required grounding is requested;
- mix source-resolution identity with capability/effect semantics.

Those mechanisms remain valid for ordinary tools/resources, but they are not the default Context Intelligence boundary.

## Selected runtime architecture

The runtime path is:

```text
Application / domain controller
  owns semantic work need
        |
        | ContextRequirement  (fields finalized by BB-061)
        v
Core runtime context-resolution seam
  owns WHEN context is required for execution
        |
        | injected resolver port
        v
Oracle package
  owns HOW bounded context is resolved
        |
        +--> repository / accepted-artifact providers
        +--> future lexical / semantic-code / graph providers
        +--> future retrieval planner
        |
        v
ContextResolution              (fields finalized by BB-061)
  provenance + currentness + budget/materialization evidence
        |
        v
Core context projection
  -> existing renderAgentContext(...)
  -> strategy/model
```

The semantic resolver is **not** a capability, Resource, LiveObject or context-block implementation. Core consumes it through dependency injection; Core does not import Oracle provider implementations.

BB-060 establishes the physical package/provider ownership and this composition boundary. It deliberately leaves the production `ContextRequirement / ContextResolution` schema and Core hook to BB-061, so BB-060 cannot create an untyped “temporary” resolution API that immediately becomes debt.

```text

  src/index.js
  src/providers/
    repository-source.js
    application-artifact-source.js
  test/
    compatibility-providers.test.js

packages/agentic-system/
  src/oracle.js                compatibility/application adapter only
  package.json                 depends on @exharness/oracle
  test/
    oracle-package-integration.test.js

test/
  oracle-context-intelligence-architecture.test.mjs

scripts/oracle-context-intelligence/
  bb060-runtime-seam-probe.mjs
```

Provider modules receive already-parsed source requests and injected readers. They do **not** import Agentic Application schemas, Core, work lifecycle, acceptance or recovery code. The Application compatibility adapter keeps the current exports `resolveBackendContext` and `resolveQaContext`, parses WorkOrders above Oracle, delegates source reads to the infrastructure package, then validates the existing Application context schemas.

This preserves current behavior while making the moved readers future provider building blocks rather than declaring them to be the final Oracle resolution API.

## Dependency rule

Allowed compile-time direction for BB-060:

```text
agentic-system  --->  @exharness/oracle
core-harness    -X->  @exharness/oracle
@exharness/oracle -X-> agentic-system
@exharness/oracle -X-> core-harness
```

The future runtime link is composition-time injection, not Core importing Oracle implementation. BB-061 may introduce a deliberately shared semantic contract, but BB-060 must not guess that contract.

## External evidence comparison

### Uber Context Graph — architecture evidence

Uber reports that agents spend much of their work locating information and describes an internal AI Context Graph spanning 24M nodes, 80M edges, 86 node types, 117 edge types and more than 30 internal systems. In its same-model example, graph grounding found the correct cross-system answer while the ungrounded path searched code/subagents and failed.

**Use:** evidence that context relationships/current organizational data can be runtime infrastructure rather than prompt decoration.

**Do not copy:** Uber's graph scale, node taxonomy, storage topology or natural-language graph query layer. ExHarness first needs a source-agnostic requirement/resolution boundary and measured provider value.

Primary source: https://www.uber.com/gb/en/blog/efficient-software-factory/ (2026-08-27).

### Aider repo-map — budgeted projection pattern

Pinned source: `Aider-AI/aider@5dc9490bb35f9729ef2c95d00a19ccd30c26339c`, Apache-2.0, GitHub search confirms stars >=1,000 at the 2026-09-26 evidence check.

Aider builds a structural repository map and ranks the most relevant portions to fit a token budget. This supports separating **retrieval/materialization** from the final **bounded prompt projection**.

**Use:** pattern for budget-aware context projection and structural relevance.

**Do not copy:** repo-map as the universal Oracle backend; it does not solve accepted-artifact provenance, cross-system currentness or durable resolution identity.

### Serena / SolidLSP — semantic-code provider pattern

Pinned source: `oraios/serena@7a2968335f2198b966864de1ce3655c8e485a653`, GitHub search confirms stars >=1,000 at the 2026-09-26 evidence check.

Serena demonstrates symbol-level semantic retrieval via LSP and relationship-aware code queries. Its current licensing is important: the Serena application is GPL-3.0-or-later while the SolidLSP component is MIT.

**Use:** evidence that semantic symbol retrieval is a useful provider capability and that a provider can be separate from the agent loop.

**Do not select in BB-060:** full Serena is not adopted as an ExHarness dependency. Reuse/inspiration or SolidLSP separation is a BB-062 provider/license decision.

### Zoekt — high-recall lexical baseline

Pinned source: `sourcegraph/zoekt@153817f643cde8b229ee388c1dddbcf07f4798af`, Apache-2.0, GitHub search confirms stars >=1,000 at the 2026-09-26 evidence check.

Zoekt supplies fast trigram-indexed source search with code-aware ranking and multi-repository support.

**Use:** a likely cheap/high-recall comparison arm for BB-062.

**Do not select in BB-060:** source indexing/update/currentness and semantic recall must be measured against the representative corpus first.

Graphiti (`getzep/graphiti@ba4a9cb32495b6864160616f8dfa2b898f4a500c`, Apache-2.0, GitHub search confirms stars >=1,000) and Cognee (`topoteretes/cognee@eb90d03740755f5252b8b12cce91fd09970f2d81`, Apache-2.0, GitHub search confirms stars >=1,000) remain BB-062/063 graph/currentness experiment inputs, not BB-060 dependencies.

## Rejected alternatives

1. **Move the two functions and call the topic complete.** Rejected because it reproduces the superseded thin-IO architecture and gives Core no runtime context seam.
2. **Make Oracle a model-visible capability/resource.** Rejected as the default because required grounding would become model/tool-call behavior and mix retrieval with effect semantics.
3. **Implement Oracle as a dynamic context block.** Rejected because rendering is not durable resolution identity/currentness; it also gives the block only rendering metadata rather than a semantic requirement contract.
4. **Make Core import `@exharness/oracle`.** Rejected because it physically couples generic runtime to infrastructure implementation and makes later provider evolution a Core dependency.
5. **Choose Graphiti/Cognee/Serena/Zoekt now.** Rejected until BB-062 measures provider value, integration/update behavior and licensing on the same corpus.

## Falsifiable BB-060 worker probe

The worker adds a **development-only** `bb060-runtime-seam-probe.mjs`. It does not introduce the BB-061 production contract.

The probe composes:

```text
semantic-need fixture
  -> injected resolver function
  -> new Oracle compatibility provider
  -> source/provenance result fixture
  -> projection into existing Core context block
  -> renderAgentContext
```

It must prove:

- resolution happens outside capability/resource/live-object invocation;
- no source-specific reader API is visible from the Core projection call;
- exact sourceRef/provenance survives projection;
- current context serialized output stays within the declared Core policy;
- Oracle provider modules import neither Agentic Application nor Core;
- Application compatibility resolvers preserve the current Backend/QA output and failure shape.

This probe establishes architectural feasibility only. It does not claim a production ContextRequirement/ContextResolution contract or live model value.

## Retained vs superseded

Retained:

- infrastructure physical ownership;
- acyclic dependency direction;
- sourceRef/provenance preservation;
- fail-closed source errors;
- current Backend repository and QA accepted-artifact flows as compatibility cases;
- Application/domain acceptance/publication/recovery authority.

Superseded:

- exactly two concrete pulls as the final Oracle architecture;
- no source-agnostic runtime resolution contract;
- no retrieval lifecycle/runtime resolution;
- package extraction alone as Oracle phase closure.
