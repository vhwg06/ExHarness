# BB-101 — Durable crash/resume of a supervised agent-tool run

Status: RESEARCH INPUT; no implementation authority.

## Outcome

A supervised agent-tool run can crash and resume the same semantic attempt: same worktree identity, same tool session, same Core session and same candidate sha, without minting a second lineage or changing the source repository.

## Current gap

- **DELIVERED_TRUTH.** `runSupervisedTask` always `mkdtemp`, uses `sessionId = agent-task:${id}:${randomUUID()}`, and disposes the worktree in `finally`. Core journals each `RUN_AGENT_TOOL` ACT, but the worktree path and tool session are not durable.
- **Executed probe** `docs/blackboard/evidence/BB-100/productization-probe-result.json`: `sessionIdUsesRandomUUID`, `disposesWorktreeInFinally`, `noResumeWorktreeOption`.
- **PLANNED_CONTRACT.** BB-066 recovers an OpenHands domain-runtime attempt, not this supervisor.

## Research questions

1. What identity is the semantic attempt: task id, worktree path, Core sessionId, tool sessionRef, candidate sha?
2. Which Core persistence seam resumes the same session after process death?
3. How does default `runSupervisedTask` stay byte-identical when no handle is requested?
4. What fail-closed checks prevent a fresh mkdtemp from masquerading as resume?

## Approaches and evidence

- **Selected: explicit handle file** next to the worktree, opt-in via `recoveryDir`. Default path still mkdtemp+dispose.
- **Rejected:** treating Core in-memory sessionStore as crash recovery; reconstructing a worktree from the source repo at a later HEAD.
- **Compare at READY:** `createResumableAgentRuntime` vs a file-backed `sessionStore` injected into `createHarness`. Research must pin one delivered Core seam.

## Discriminating experiment

Fake CLI FIX_AFTER_FEEDBACK. Kill the Node process after attempt 1 ACT (tree dirty or candidate created, verification GAP). A fresh process given the handle must resume, apply the fix on attempt 2, and PROMOTE the same task id. A handle whose worktree was deleted, or whose digest was rewritten, must refuse.

### Probe findings

- **Default supervisor (DELIVERED_TRUTH).** `runSupervisedTask` options are `tool, task, model, maxAttempts, timeoutMs, maxFeedbackChars, permissionProfile, env, eventSinks, tracer, invocationObserver`. There is no `recoveryDir`, no `resumeSupervisedTask` / `disposeRecoverableRun` export, no `AGENT_TOOL_RUN_HANDLE_VERSION`, and `createHarness` is not given a `sessionStore`. Session id is still `agent-task:${task.id}:${randomUUID()}`, scratch is `mkdtemp(join(tmpdir(), "exharness-agent-"))`, and `finally` disposes the worktree.
- **`invocationObserver` (DELIVERED_TRUTH, BB-098).** Default null; with it null the supervised result is unchanged. Recovery must pass it through. Existing BB-097/BB-098 tests stay the contract for the default path.
- **Core crash-resume seam (DELIVERED_TRUTH).** `createHarness({ sessionStore })` with `{ load, save, supportsRevisions: true }` persists AVO work state and the action-effect journal. `createJsonBackendSessionStore({ directory })` (agentic-system, same port) survived a new `createHarness` instance: `resume(sessionId)` saw the same id. `start()` rejects `session already exists`. A RUNNING variation makes `vary()` throw `RecoveryRequiredError` (`code: RECOVERY_REQUIRED`); `recover(sessionId, { force: true })` closes it as INTERRUPTED and a later `vary()` completes. `createInMemorySessionStore()` is the contract template and is not crash recovery.
- **`createResumableAgentRuntime` is not the seam.** It is a runtime-snapshot factory (`snapshot`, `runtimeCompatibilityTag`, `strategy`, resource/live-object rebind). It has no `start` / `vary` / `resume` session API.
- **Worktree reopen (DELIVERED_TRUTH).** `createLocalGitWorkspace` always `git worktree add --detach`. A second add on the same path fails. There is no delivered reopen helper; recovery must wrap an existing worktree itself and must not call `worktree add` on resume.
- **Tool resume (DELIVERED_TRUTH).** Codex `exec resume <sessionRef> --json -`. Kiro `--resume` and agy `--continue` are cwd-scoped; `sessionRef` is ignored. Fake CLI `FIX_AFTER_FEEDBACK` still exists. `canonicalJson` is already exported from `run-trace.js`.
- **Strategy loop.** `createSupervisedAgentStrategy` options are `task, maxAttempts, maxFeedbackChars`; the loop is `for (let index = 1; index <= maxAttempts; index += 1)` with ACT then every verifier then EVALUATE. Core `act()` saves `currentCandidate` only after `environment.act` returns, so a durable handle must be written after the ACT capability returns, not inside `invocationObserver`.

### Draft researchGap resolution

Draft gap: *Pin the delivered Core persistence export used for crash resume (file-backed sessionStore versus createResumableAgentRuntime) before READY; in-memory is not sufficient.*

**Resolved.** Use `createHarness({ sessionStore, recoveryPolicy: { staleAfterMs: 0 } })`. Implement `createFileSessionStore({ directory })` in `packages/agent-tools/src/recovery.js` with the `createInMemorySessionStore` contract (`load` / `save` / `supportsRevisions: true`), persisting under `recoveryDir/core-session/` and using `StoreConflictError` plus `normalizePersistentState` from `@exharness/core-harness`. Do not call `createResumableAgentRuntime`. Do not import `createJsonBackendSessionStore` (Backend `supportsDurableRecovery` execution authority). On resume: never `harness.start` (it throws `session already exists`); `harness.recover(sessionId, { force: true })` then `harness.vary(sessionId)`. Same `coreSessionId` = `agent-task:${task.id}`.

No remaining research gap. No PLAN_INPUT_CONTRADICTION: Core persists across process death when a file-backed revision-aware `sessionStore` is injected.
