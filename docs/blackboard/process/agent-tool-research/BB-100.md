## Research questions

1. Should composition inject `createSupervisedAgentStrategy` into `createBackendWorker`, or map `BackendWorkOrder` to `AGENT_TASK_V1` and call `runSupervisedTask`?
2. Which evaluate rule is acceptance on this path: mutation-only (BackendWorker) or verifier PASS (agent-tools)?
3. How is `BackendWorkResult` projected without claiming APPLIED on EXHAUSTED/TOOL_UNAVAILABLE/NO_CHANGE?
4. What stays unchanged on the default CodeAct path?

## Approaches and evidence

- **Selected: mapping adapter.** Probe shows different ACT kinds (`workspace.act` vs `RUN_AGENT_TOOL`) and different evaluate rules. Injecting the supervised strategy into BackendWorker would silently weaken or replace mutation-only evaluate.
- **Rejected:** replacing BackendWorker evaluate globally; wrapping the CLI as `model.generate()`.
- **Deferred:** wiring `runBackendThenQaObjective` / durable Backend→QA (BB-104); DomainExecutionController OpenHands (BB-066).

### Findings

- **BackendWorkResult status enum.** `BackendWorkStatus` is `{ APPLIED, BLOCKED, FAILED }`. `BackendWorkResultSchema.parse` accepts a hand-built `APPLIED` object with `revision` a 40-hex sha; it does not require `createBackendWorker`. Parsed keys are `status`, `summary`, `revision`, `artifacts`, `evidence`, `gaps`, `blockers`. There is no `reason` field. `BLOCKED` requires a non-empty `blockers` array; `["TOOL_UNAVAILABLE"]` parses. `APPLIED` without `revision` is rejected.
- **Acceptance vs completion.** Default `assessBackendCompletion` on `APPLIED` with empty evidence/artifacts returns `CONTINUE`. The same result with `backend.mutation` + `backend.typecheck` + `backend.tests` PASS artifacts plus at least one `git:<sha>:<path>` artifact returns `ACCEPT`. `BackendEvidenceClaim` values are `backend.mutation`, `backend.typecheck`, `backend.tests`. `mutationEvidence` in `backend-worker.js` is private; Core exports `createEvidenceArtifact`, `evidenceFromVerificationArtifact`, `subjectFromValue`, `environmentRefFromValue`.
- **AGENT_TASK_V1.** `validateAgentTask` freezes `{ id, repositoryRoot, baseRevision, prompt, verifications }` (`verifications[]` = `{ name, command, args, timeoutMs }`). `AgentTaskStatus` is `{ ACCEPTED, EXHAUSTED, TOOL_UNAVAILABLE }`. `AttemptOutcome.NO_CHANGE` is an attempt field, not a result status.
- **BackendContext has no filesystem path.** Parsed `context.repository` is `{ ref, revision }` (probe used `repo://probe`). `repositoryRoot` for `AGENT_TASK_V1` is a caller path. `BackendWorkOrder` keys are `id`, `objectiveId`, `task`, `repositoryRef`, `revision`, `requiredFiles`, `constraints`. Prompt source is `order.task`.
- **Supervised outcomes (fake CLI).** `FIX_FIRST` → `ACCEPTED`, source HEAD/refs/status unchanged, `acceptedSha` still `git cat-file`-reachable after dispose, and `createLocalGitWorkspace` + `createLocalCommandVerifier` at that sha records `PASS` with `revision=<acceptedSha>`. `NEVER_FIX` → `EXHAUSTED` with `claimedSuccess: true`. `CLAIM_SUCCESS_NO_EDIT` → `EXHAUSTED`, outcomes `NO_CHANGE`/`NO_CHANGE`, `claimedSuccess: true`, `mutated: false`. `AUTH_FAIL` → `EXHAUSTED` (not `TOOL_UNAVAILABLE`). Missing executable → `TOOL_UNAVAILABLE`, `acceptedSha: null`.
- **BB-098 supervisor.** `runSupervisedTask` options are `tool`, `task`, `model`, `maxAttempts`, `timeoutMs`, `maxFeedbackChars`, `permissionProfile`, `env`, `eventSinks`, `tracer`, `invocationObserver`. `invocationObserver` defaults to null; the probe's observer ran and saw `CANDIDATE_CREATED`. Evaluate is still verifier-PASS; claimedSuccess is telemetry. `supervisor.js` imports `../../agentic-system/src/index.js`. `backend-worker.js` and current `agentic-system/src/index.js` do not import agent-tools. Result fields: `taskId`, `tool`, `toolVersion`, `status`, `attempts`, `acceptedSha`.

### How each draft researchGap was resolved

Draft gap: "Confirm delivered BackendWorkResultSchema status names (APPLIED/FAILED/BLOCKED or equivalent) and bind D3 to those exact identifiers before READY."

Resolved: the names are exactly `APPLIED` / `FAILED` / `BLOCKED`. Projection is `ACCEPTED` → `APPLIED` (after re-ground), `EXHAUSTED` (including `NO_CHANGE` attempts, `NEVER_FIX`, `AUTH_FAIL`) → `FAILED`, `TOOL_UNAVAILABLE` → `BLOCKED` with `blockers: ["TOOL_UNAVAILABLE"]`. The draft contradiction ("cannot represent APPLIED without createBackendWorker evaluate") is false: the schema is a parser, and the probe parsed `APPLIED` without constructing a BackendWorker.
