# BB-097 — Run Codex, Kiro and agy under ExHarness supervision

Status: RESEARCH INPUT; no implementation authority.

## Outcome

A supported CLI coding agent (Codex, Kiro or agy) can be dispatched by ExHarness on a real local git repository. ExHarness owns candidate identity, verification, bounded retry with verification feedback, and promotion. The agent only edits the isolated worktree, and its own claim of success is never acceptance.

## Current gap

- **DELIVERED_TRUTH.** Core composes `createHarness({ strategy, environment, verifiers, eventSinks, tracer })`. No adapter launches an external coding agent. No agentic test exercises a real workspace; see the BB-096 probe.
- **PLANNED_CONTRACT.**
  - BB-096 (READY) plans `createLocalGitWorkspace` and `createLocalCommandVerifier`.
  - BB-066 (READY) plans an OpenHands runtime adapter under `DomainExecutionController`. It names no Codex, Kiro or agy adapter.
- **Executed probe** `docs/blackboard/evidence/BB-097/agent-cli-probe.mjs` (help and version commands only, no provider calls):
  - All three CLIs are installed: codex-cli 0.158.0, kiro-cli-chat 2.24.1 and agy 1.1.1.
  - All three expose a non-interactive mode: `codex exec`, `kiro-cli chat --no-interactive` and `agy --print`.
  - All three can resume a session: `codex exec resume --last`, `kiro-cli chat --resume` and `agy --continue`.

## Research questions

1. **Integration mode.** Should ExHarness supervise the tool from outside, or should the tool call ExHarness from inside (MCP tools or lifecycle hooks)?
2. What does one agent invocation map to in AVO: ACT, verify, EVALUATE, then PROMOTE or retry with feedback?
3. How are argv, permissions, timeouts and outputs normalized across three different CLIs without using a shell?
4. How is the source repository protected when the agent runs with auto-approved edits?

## Approaches and evidence

- **Selected: outer supervision.** It works the same way for all three tools because it relies only on the probed non-interactive and resume surfaces, and ExHarness authority cannot be bypassed.
- **Deferred: in-tool MCP/hook gate.**
  - Blocking-completion semantics differ per tool and version.
  - Codex hooks are documented, but no `~/.codex/hooks.json` exists here.
  - Kiro 2.24 uses the 2.x hook format.
  - agy hooks live under `~/.gemini/config`.
  - Installing into the user's real config is unsafe.
  - This mode can become a later arm once BB-099 shows whether verification feedback adds value.
- **Rejected:** wrapping a CLI as `model.generate()`. Core needs one JSON action per turn, and the CLIs are complete agents with their own tool loop.
- **Reuse:** the BB-096 workspace and verifier provide commit identity and revision-bound verification. BB-097 adds only the tool adapters and the supervisor strategy.

## Discriminating experiment

Deterministic fake CLIs (`node` scripts that impersonate each tool's argv and output contract) run inside a temporary git repository. The supervisor must:

- ACCEPT only after verification passes;
- feed failures back through resume;
- stop at `maxAttempts`;
- kill a hung tool at its timeout;
- fold commits made by the agent into one candidate;
- never touch the source repository.

A live smoke test per tool is opt-in only and needs the user's authenticated CLI.
