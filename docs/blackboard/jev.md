# Jev evaluation and delivery

The outer Blackboard has two contracts: OBJECTIVE -> READY_IMPLEMENT_PLAN through RESEARCH_SA, and exact READY_IMPLEMENT_PLAN -> DELIVERED_FEATURE through WORKER. Jev is the semantic judge for both. This tooling does not itself attest that a feature has been delivered.

## API and evidence

The trusted Node evaluator calls `POST https://api.typesafe.ai/v1/systemone` using `TYPESAFE_API_KEY`. For local use, copy `.env.example` to `.env` and fill the value after `TYPESAFE_API_KEY=`; `.env` is ignored by Git. An already exported shell or CI variable takes precedence. It sends one `{model,state,questions}` batch. Model is pinned to `jev-1.13.0`; aliases and unexpected returned models fail closed. See the [provider API](https://docs.typesafe.ai/api) and [atomic question guidance](https://docs.typesafe.ai/primitives).

The state includes the objective, semantic plan and bounded source/evidence contents, not a whole conversation or bare references. Readiness reads source at `contract.researchBaselineSha`; updating that exact baseline is an explicit research change. Large research sources are represented by deterministic bounded excerpts (head, structural outline and tail) while the evaluation state retains the hash and byte length of the complete file, so any hidden source change still invalidates the semantic cache. Research payloads also use a conservative byte ceiling below the provider's token context limit. Worker reads source from the exact candidate commit, includes changed surfaces and required seams/tests, and checks plan scope. A worker plan must also declare `livingDocs.refs`, all of which must be under `docs/living/`, inside the authorized write scope, listed as consolidated refs, and changed by the candidate. The worker payload includes their full document bodies and adds the plan's Living Docs statement as an independent Jev Choice question. When a worker payload is batched (see below), the Living Docs question receives each doc's preamble plus every whole section the candidate added or modified, not a fixed heading selection, together with the delivery evidence the docs are checked against (`LIVING_DELIVERY_EVIDENCE_V4`). Verification logs bind command, successful exit, candidate identity and content hash. Additional criterion evidence is attached through `contract.claimEvidence`.

Negative cases are bound, not inferred from whole-log success. When a plan declares `negativeCaseBindings`, readiness adds a `readiness-negativeCaseBindings` question. Collection (`scripts/blackboard-negative-case-binding.mjs`) checks that each bound title passed in its log and that its body invokes `subjectSymbol` without always-true assertions. An invocation is a direct call (`subject(…)`, `subject?.(…)`, `new subject(…)`), or, when the subject is an object such as an adapter or facade, a call to one of its methods (`subject.method(…)`). Property reads and calls on another object's `subject` member do not count. Worker materialization re-extracts each body at the candidate SHA, checks its recorded hash, adds `state.negativeCaseEvidence` and asks one atomic question per binding id. `jev-policy.json` `negativeCaseBindingsFromWorkId` makes bindings mandatory from that work id onward (materialization fails before any provider call). Earlier work is grandfathered. Verdict rules and confidence-as-telemetry are unchanged. Verification commands run without an inherited `NODE_TEST_CONTEXT`, so nested logs keep their plain reporter format.

The CI selector treats a fully bound `RESEARCH_SA/SATISFIED` readiness publication that advances the same semantic plan to `WORKER/EXECUTION` as a control-plane publication, not a new research candidate. Any other lane/routing mutation in a research candidate fails closed. Before ordinary research routing, the selector detects new or changed `OBJECTIVE_SUPERSESSION` receipts and emits them as `supersessions`. The target and its direct dependents are then excluded from Jev work and judged only by deterministic verification. Outside such a receipt, any change to trusted objective bytes of contracted work fails selection, so a candidate can never redefine its own evaluation subject.

Questions are independent Choice questions. All must select SATISFIED to pass. IMPLEMENTATION_DEFECT and INSUFFICIENT_EVIDENCE return to worker repair; PLAN_INPUT_CONTRADICTION returns upstream. Research findings always stay in research. Confidence does not change the selected outcome. Invalid response shape, missing claims, model mismatch, missing evidence or stale hashes block publication.

Payload budget is 512 KiB per provider request, configured in `jev-policy.json` (`maxPayloadBytes`; research requests are further capped at 98,304 bytes). A payload that is sent whole (every research payload, and a worker payload within the 60,000-byte batch limit) must fit it. A larger worker payload is never sent whole: only its bounded per-question batches are, so the budget applies to each batch. `materialize()` builds the exact batch manifest that evaluation will use (`checkPayloadBudget`) and fails closed, before any provider call, when a batch cannot fit. The full materialized state stays local and is bound by `stateHash`/`cacheKey`; its total size is not a provider input. Exceeding a request budget requires more precise evidence selection; the tool does not silently truncate mandatory coverage.

A worker payload over the 60,000-byte batch limit is judged one atomic question per request. A question that fits is sent exactly as before (`WORKER_ATOMIC_QUESTIONS_V1`), so existing evaluations keep their identity. If a question's batch is still over the limit, each evidence log larger than 8,192 bytes is replaced in that batch by a deterministic `EVIDENCE_LOG_EXCERPT_V1` excerpt. The excerpt keeps the command, the exit status, summed test counts, failing test names, npm script markers and head/tail lines, plus the full log's `hash` and byte length. The full log stays in `docs/blackboard/evidence/<WORK_ID>`, and the full materialized state (and so `stateHash`/`cacheKey`) still binds its complete content. If the excerpted batch still does not fit, the question's evidence files are split in ref order into bounded parts. Each part carries a `state.batch` descriptor and every other file's hash, and each part is a separate request. A split criterion question is `SATISFIED` only when every part is `SATISFIED` (the least confident part answer is kept). Otherwise the most severe part answer wins (`PLAN_INPUT_CONTRADICTION` > `IMPLEMENTATION_DEFECT` > `INSUFFICIENT_EVIDENCE`). The Living Docs question instead compacts before it splits and aggregates per-part (see `LIVING_DELIVERY_EVIDENCE_V4` below). Evaluations that use excerpts or parts record strategy `WORKER_BOUNDED_EVIDENCE_V2`, a manifest with `excerpted` refs and `part`/`parts`, and per-part choices. Validation recomputes that manifest and strategy. A single part that cannot fit, or a question whose non-evidence input alone exceeds the limit, still fails closed. The limits are not raised.

Living Docs in a batched worker evaluation. `materialize()` derives, from the bound `baselineSha..candidateSha`, the candidate-side changed line ranges of each `livingDocs.refs` file. It uses `git diff --unified=0` with a pinned algorithm and no external diff or textconv, so local git configuration cannot change the ranges. The ranges are returned beside the input as `livingChanges`. They are not part of the semantic state, so `stateHash`/`cacheKey` are unchanged. For the Living Docs question, each doc is sent as its preamble plus every whole `##`/`###` section that contains a changed line (headings inside fenced code are ignored, and blank separator lines alone do not mark a neighbouring section). Omitted runs of unchanged sections are replaced by an explicit marker. The entry keeps the full document's `hash` and `bytes`, `excerptStrategy: LIVING_CHANGED_SECTIONS_V2`, the `changedSections` headings and `omittedSections`. A doc with no changed lines falls back to the earlier selection. Criterion questions keep the earlier selection byte-for-byte. The Living Docs batch then goes through the same evidence excerpt/part mechanism and 60,000-byte limit, and input that still cannot fit fails closed. A missing or malformed change map, or an unknown strategy, fails closed.

Delivery evidence for the Living Docs question (`LIVING_DELIVERY_EVIDENCE_V3`, retained). A Living Docs claim ("the docs accurately describe the delivered implementation") cannot be judged from the docs alone. Under `LIVING_CHANGED_SECTIONS_V2` the Living Docs batch only received verification runs whose command was exactly `node --test <expectedTest>`, and only those runs' logs, so a candidate verified through `npm run …` commands reached Jev with no runs, no evidence files and no implementation sources (BB-090's Jev run correctly answered `INSUFFICIENT_EVIDENCE`). V3 keeps the V2 Living Doc section selection and adds, deterministically and within the same 60,000-byte batch limit:

- every plan verification run (`state.verification`), and every evidence file, each log above 3,072 bytes replaced by the compact hash-bound evidence excerpt (command, exit status, test totals, failing names, head and tail);
- the evidence claims (`state.evidence`) and a plan projection with scope, source seams, the Living Docs declaration, every acceptance criterion with its `verificationIds`, and the verification plan, so each doc statement can be traced to a criterion and its run;
- hash-bound excerpts of the candidate's changed lines in its changed non-doc sources (`CANDIDATE_CHANGE_EXCERPT_V1`). `materialize()` derives `candidateChanges` from the bound `baselineSha..candidateSha` with the same pinned diff options as `livingChanges` and returns it beside the input, outside `stateHash`/`cacheKey`. Each changed body must hash to the source hash bound in the evaluation state, so the excerpt cannot drift from the judged candidate; deleted and binary files carry no body. An excerpt lists numbered changed lines, outline lines first (declarations/exports, comments, headings, test titles), then fail-closed lines (`fail(`/`throw`), then the remaining changed lines in order, with `…` marking gaps and an explicit marker plus `omittedChangedLines` when lines are left out. Each excerpt is at most 3,072 bytes and all excerpts together at most 18,432 bytes; implementation sources are taken before tests, each group in ref order, and sources beyond the budget stay hash stubs;
- a `state.livingEvidence` note naming the strategy and stating that omitted content is bound by hash.

A missing or malformed change map, a body that differs from the bound source hash, a changed ref outside the materialized sources, or a batch that still exceeds the limit fails closed. Criterion questions are unchanged by V3.

Cohesive evidence for the Living Docs question (`LIVING_DELIVERY_EVIDENCE_V4`, current). V3 splits the evidence files across parts when its base exceeds the 60,000-byte limit, and every part is then judged against the whole doc claim, so a part holding only unrelated regression logs answers `INSUFFICIENT_EVIDENCE` and fails the whole question even when the docs are accurate (BB-055: `LIVING_DOCS` part choices `[INSUFFICIENT_EVIDENCE, INSUFFICIENT_EVIDENCE, INSUFFICIENT_EVIDENCE, SATISFIED]` over 4 parts while all 17 criteria were `SATISFIED`). V4 keeps the claim-proving evidence together before any split, in deterministic stages. The first stage is the V3 base byte-for-byte except the strategy record; then the changed-source excerpt budget is lowered progressively (18,432 → 9,216 → 4,608 total bytes, never below 768 per file, implementation sources before tests, each group in ref order); then evidence logs above 1,536 bytes use the smaller compact hash-bound excerpt `EVIDENCE_LOG_COMPACT_EXCERPT_V1`, which keeps command, exit status, test totals, failing test names and the passing test names or titles (the tests the docs cite are the proof), plus head/tail lines. The first stage that fits in one part is sent whole, carrying every evidence log; only a base that still cannot fit is split, in the same ref order as criterion splits.

A split Living Docs question is the only question with per-part aggregation. Each part carries Living Docs-only instructions: judge whether the evidence in this part proves or contradicts the doc claims; do not answer `SATISFIED` when anything in the part contradicts the docs (a contradiction is `IMPLEMENTATION_DEFECT`); answer `INSUFFICIENT_EVIDENCE` when the part's evidence is unrelated to the claims. Aggregation: any contradiction (`IMPLEMENTATION_DEFECT`, or the more severe `PLAN_INPUT_CONTRADICTION`) in any part fails the question and the most severe one wins, so a real doc defect still fails and is never outvoted by unrelated parts; otherwise `SATISFIED` when at least one part is `SATISFIED` (the least confident satisfied part is kept); otherwise `INSUFFICIENT_EVIDENCE`. Ordinary criterion and negative-case questions keep all-parts-must-pass. `state.livingEvidence` records the strategy with the engaged `changeBudget` and `logBytes`.

Source selection for criterion questions (`CRITERION_RANKED_SOURCE_V2`, retained). Each criterion question of a batched worker evaluation receives up to five relevant candidate sources. Sources up to 4,000 characters are sent whole. The original selection (`CRITERION_TERM_LINES_V1`) took every line containing any criterion word, in file order, until 2,800 characters. Generic words such as "the", "and", "set" or "new" match almost every line, so for a large new module this degenerated into the file head. BB-082's CONTRACT and RETENTION questions never saw the receipt schema or the retained-receipt check, and Jev correctly answered `INSUFFICIENT_EVIDENCE`. V2 ranks the lines of each larger relevant source instead:

- each criterion term is weighted by how rare it is in that file;
- common English and JavaScript words, and terms found on more than 20% of the file's non-empty lines, carry no weight;
- a line's score is the sum of its term weights, doubled when the candidate changed the line (from `candidateChanges`), plus a small bonus for declaration, comment and test-title lines;
- the first three lines are kept, then the highest-scoring lines (ties in line order), each with the preceding line and up to three following lines, until 4,000 characters;
- the excerpt lists numbered lines in file order with `…` at gaps and keeps the full source `hash` and `bytes`.

Selection is deterministic. A missing or malformed change map, or an unknown strategy, fails closed. The Living Docs question is unaffected.

Changed-source selection for criterion questions (`CRITERION_CHANGED_SOURCES_V3`, retained; V4 keeps its source selection). The full worker state sends a full body only for Living Docs refs and the plan's `sourceSeams.expectedNew` and `expectedTests`; every other source is a hash stub. V2 considers only sources that already have a body and keeps one only when its filename shares a criterion term. So when a candidate changes an existing implementation file that is not listed as new, its criterion questions never see the change. For BB-089, AD1–AD4 received `oracle.js` and the new requirements module only as `OMITTED` stubs, while the tests and Living Doc arrived whole. V3 differs from V2 in three ways:

- a source is eligible when it has a body, or when `candidateChanges` holds a body for it whose hash equals the bound source hash (a mismatch fails closed);
- a candidate-changed source scores its V2 filename score plus 12, plus one point per distinct non-stop criterion term found in its body (at most 10); tests run by a selected command still score 100;
- up to six sources are sent; each is sent whole up to 3,000 characters, otherwise as the V2 ranked excerpt bounded at 3,000 characters and marked `excerptStrategy: CRITERION_CHANGED_SOURCES_V3`.

Unchanged stubbed sources stay stubs. The Living Docs question is unaffected.

Change-set evidence for criterion questions (`CRITERION_CHANGE_SET_V4`, current). V3 criterion questions could not judge two recurring parts of a criterion. BB-089's AD4 (paid run on `caa663c2`, `INSUFFICIENT_EVIDENCE` 0.61 with the other four questions `SATISFIED`) required "only authorized files change" and "the Oracle workflow Living Doc describes the opt-in path, its budget difference and the unthreaded durable workflow". But the question had no changed-file list and no write scope, and it received the Living Doc's scoped selection (preamble plus heading matches), which contained none of the changed sections. V4 keeps V3's source selection and adds:

- `state.changeSet` on every criterion question: `refs` (every file in `git diff --name-only baseline..candidate`, sorted), the plan's `sourceScope.write` and `forbiddenWrite`, and instructions stating that the trusted gate checked each ref against that scope before the evaluation. The change set is derived from the bound commits and is not part of `stateHash`. The evaluation path fails closed when it is missing, and a malformed one fails closed.
- For a criterion whose statement or `evidenceRequired` names the Living Docs (`living doc` / `living docs`), each Living Doc in the plan's change map is sent as its preamble plus every section the candidate changed, the same selection as the Living Docs question. A missing or malformed change map fails closed. Other criteria keep the scoped selection.
- Before splitting a criterion's evidence into parts (each part is judged against the whole criterion), every log larger than 3,072 bytes is replaced by the compact hash-bound excerpt the Living Docs question uses. The criterion is split only when that still exceeds the 60,000-byte limit.

New batched worker evaluations record `metrics.batching.criterionSourceStrategy: CRITERION_CHANGE_SET_V4`. Retained evaluations validate with the strategy they recorded (`CRITERION_RANKED_SOURCE_V2` or `CRITERION_CHANGED_SOURCES_V3`), or with the original selection when the field is missing, byte-for-byte against their own manifest. `publish:blackboard-evaluation` rejects a new batched worker evaluation that does not use the current criterion source strategy.

Negative-case questions in bounded batches (`NEGATIVE_CASE_EVIDENCE_V1`). A worker payload above the batch limit is sent one question at a time. Before this fix, a negative-case question's batch was built as if it were a criterion without a claim: it carried no `state.negativeCaseEvidence`, no verification run and no evidence log, so its instruction pointed at state the model never received. Every such question then came back `INSUFFICIENT_EVIDENCE`. The first batched worker evaluation with bindings (BB-101) returned 7 of 7 negative cases that way while every criterion was `SATISFIED`. Now each negative-case batch carries four things: its own `state.negativeCaseEvidence` entry (the hash-checked extracted test body), the binding in `plan.negativeCaseBindings`, its parent criterion, and only the verification run and log the binding names. The binding's `testRef` is ranked as that question's test source. A binding whose run or criterion is missing fails closed. Criterion and Living Docs batches are byte-identical to before. No retained batched evaluation had negative-case questions, so no retained manifest changes.

Omitted-source index (`OMITTED_SOURCE_INDEX_V1`, last resort). A large candidate (a new package, a sealed evidence tree and a retired directory) can make a question's non-evidence input exceed the 60,000-byte limit on hash stubs alone: BB-065 sends 261 sources, of which 253 are stubs, plus a 261-ref change set, so every criterion question failed closed before any evidence was added. Only a question that no earlier stage can represent is rebuilt as follows, and every other batch keeps its exact payload:

- every source sent as a hash stub is removed from `state.sources` and summarized in `state.omittedSources`: count, total bytes, the hash of the exact stub list, and at most 32 directory groups with file, changed, deleted and byte counts (paths are shortened to the deepest level that yields at most 32 groups);
- on a criterion question that is not a Living Doc criterion, the scoped Living Doc background is bound by hash in the same index; the Living Docs question and Living Doc criteria keep their changed sections;
- `state.changeSet.refs` keeps only the changed files sent in `state.sources`, and `refCount`/`refsHash` bind the complete changed-file list. The trusted gate has already checked every changed ref against the write scope.

The rebuilt question then goes through the same evidence excerpt and part stages and the same limit, and input that still cannot fit fails closed. The limits are not raised, and the full evaluation state (and so `stateHash`/`cacheKey`) is unchanged. Manifest entries built this way carry `sourceIndex: OMITTED_SOURCE_INDEX_V1`, and the evaluation records strategy `WORKER_SOURCE_INDEX_V3`. Validation recomputes both.

New batched worker evaluations record `metrics.batching.livingExcerptStrategy: LIVING_DELIVERY_EVIDENCE_V4`, and validation recomputes the manifest with the recorded strategy. Retained evaluations keep validating byte-for-byte against their own manifest: `LIVING_DELIVERY_EVIDENCE_V3` evaluations with their recorded strategy, `LIVING_CHANGED_SECTIONS_V2` evaluations (BB-096, BB-053) with theirs, and evaluations without the field with the implied `LIVING_SCOPED_SECTIONS_V1` selection (A17/Integration C sections, or the first section plus up to two scope-matching headings). `publish:blackboard-evaluation` rejects a new batched worker evaluation that does not use the current strategy: `LIVING_SCOPED_SECTIONS_V1` could hide the sections a candidate changed (BB-096's `A18` section was never sent to Jev), `LIVING_CHANGED_SECTIONS_V2` could withhold all delivery evidence from the Living Docs question, and `LIVING_DELIVERY_EVIDENCE_V3` could split the claim-proving evidence across parts so unrelated logs fail an accurate doc claim (BB-055).

Research must replace generic migration verification mappings with criterion-specific commands and negative cases before readiness.

## Cache, cost and stability

Cache identity includes canonical materialized state, questions/spec, model, materializer/validator policy and lane. Keys ignore object key ordering and run metadata. Plan status and its readiness receipt are excluded from plan content hashing to avoid a circular binding. Source/evidence contents remain in the hash. A different candidate can reuse answers only when all evaluated content is identical; publication still binds the exact new subject.

Valid findings are cached as well as SATISFIED answers. Unchanged input never rerolls for acceptance. A repeated finding publication reports `noSemanticProgress`. Error responses are not cached. Cache entries are operational data under `.cache/blackboard-jev`, not canonical authority or artifact history.

API requests have a 30-second deadline and at most one transport/429/5xx retry. Auth/schema errors are not retried. Retry-After must fit within the deadline. Missing key, timeout and invalid responses cannot produce an evaluation artifact or a satisfied check. Non-success provider responses retain a bounded response body in the trusted CI error so request-shape/context failures are diagnosable without exposing credentials.

Each answer must name a criterion option, carry a probability for every option and choose a maximum-probability option. Jev reports probabilities at two decimals, so rounding n values moves their sum by up to n half-units of the second decimal: a sum within `n × 0.005` of 1 is accepted verbatim and never renormalized (four options: 0.98–1.02); a sum further from 1 is a malformed distribution, rejected after the single allowed retry.

Metrics include request attempts, cache hit, payload bytes, token usage, latency, typed distributions and estimated cost. `pricing: null` means unknown monetary cost. To estimate cost, configure model, source URL, date, inputPerMillion and outputPerMillion; never infer a price from token count alone.

`npm run eval:blackboard-jev-stability` makes three uncached runs per labeled fixture for both lanes. It reports agreement, verdict flips, false-satisfied cases, usage and cost. It never publishes canonical judgment. It requires a real API key and is excluded from normal verification.

## Local lifecycle

1. Resolve current work from the graph. Claim a schedulable task with `npm run claim:blackboard -- <WORK_ID> <WORKER_ID>`, then materialize its context using the compatibility bootstrap command.
2. Research edits the current plan draft and resolves its recorded gaps. Materialize with `npm run materialize:blackboard-evaluation -- <WORK_ID>`.
3. Copy `.env.example` to `.env` and fill `TYPESAFE_API_KEY`, or set it in the process environment. Run `npm run eval:blackboard-jev -- <WORK_ID>`. Output is `artifacts/blackboard-jev/<WORK_ID>.json`; exit 2 means findings, not API failure.
4. Publish an evaluation produced by the trusted evaluator with `npm run publish:blackboard-evaluation -- <WORK_ID> <ARTIFACT>`. The publisher rereads current bindings and serializes publication with an exclusive lock. It updates current canonical artifacts and graph in place; completed publications are idempotent. An interrupted multi-file publication fails closed and requires reconciliation of the current files before work resumes. No lock is stolen on a timeout.
5. After readiness, set exact candidateSha/baselineSha and evidenceRef on the current task. The candidate must be committed. Run `npm run collect:blackboard-evidence -- <WORK_ID>` without provider credentials. Verification runs execute plan commands; attach domain observations via claimEvidence when logs are insufficient.
6. Evaluate/publish worker claims. SATISFIED advances only to MERGE_PENDING, and includes a SATISFIED Living Docs Choice for the plan's implementation description. The publisher stores the canonical Jev evaluation beside the current plan as `docs/blackboard/artifacts/ready-implement-plan/<WORK_ID>.<readiness|candidate>-jev-evaluation.json`. Merge using a merge commit or fast-forward, preserving candidate SHA. If the integrated tree changes, verify and evaluate a new candidate first.
7. Fetch main. Record exact mergeSha and current consolidatedRefs, then run `npm run verify:blackboard-delivery -- <WORK_ID> <MERGE_SHA>`. Verify checks candidate ancestry, tree identity and evaluated source still present on main.
8. `npm run publish:blackboard-delivery -- <WORK_ID> <MERGE_SHA>` writes the canonical receipt and completes routing. Commit the canonical publication changes through the repository's normal change process. Artifact upload alone never marks work DONE.

Canonical control-plane documents and generated artifacts may differ from the candidate checkout while evidence is collected; product source must match the candidate. No source code is taken from those control-plane changes for candidate evaluation. Provider credentials must not be present during verification-command execution.

## CI

The pull-request `test` workflow is the only automatic semantic-gate surface. After kernel verification and the Living-doc impact gate pass, its internal `blackboard-gate` job selects exact WORKER/RESEARCH_SA judgment subjects or readiness publications. If semantic judgment is required, the same PR run invokes the trusted reusable `blackboard-jev.yml@main`; there is no standalone router workflow or dispatch chain. Pushes run the separate `push-test` kernel workflow and do not create automatic Jev evaluations.

`blackboard-gate` reads routing/objective authority from the exact PR-base checkout and candidate data from the exact PR head. The reusable Jev workflow receives exact work id, candidate SHA, trusted PR-base SHA and controller SHA; `collect Jev evidence` runs without TypeSafe credentials, while `Jev evaluate` alone receives `TYPESAFE_API_KEY`, calls the provider, validates the typed result and uploads `jev-evaluation-<WORK_ID>`. RESEARCH_SA may contribute only its canonical plan draft and exact research baseline. A canonical readiness-publication PR runs the sibling `readiness-verify` job in the same PR workflow instead of rerolling the provider. An objective-supersession PR runs the sibling `objective-supersession-verify` job. That job runs `blackboard-jev-ci.mjs verify-supersession` from the trusted PR-base checkout with `BASE_SHA`, and it reads the PR head only as data. It has no secrets, performs no `npm` install, calls no provider and executes no candidate code.

Download the complete result bundle from this trusted workflow and use the publication command above against the current checkout. Keep the sibling implementation-result JSON and `evidence/<WORK_ID>` directory beside the evaluation. The publisher imports the result into the canonical `docs/blackboard/artifacts/ready-implement-plan/<WORK_ID>.implementation-result.json` path and evidence into `docs/blackboard/evidence`, after checking the current candidate/plan binding and log digests, then validates the full evaluation state. Commit these canonical files with the publication so future checkouts retain the evidence.

The canonical publisher rejects stale inputs; an uploaded or manually edited JSON file is not independent proof of provider provenance. Publishing is a trusted-controller action, not a worker self-acceptance API. CI does not bypass repository merge permissions or automatically push to main.

Offline validator, routing, cache and merge fixtures run in normal verification with mock transport and no API key. Live API evaluation and stability benchmarks do not run in that matrix.

## Current-only migration

`npm run migrate:blackboard-delivery` converts unfinished work into objective/plan bindings and research drafts, retaining task identities/dependencies. DONE evidence is co-located under the ready-plan directory. Any retained source material uses `.source.json` beside the canonical objective/plan; graph bindings select only the unsuffixed current contract. No generation siblings, history chains or retrospective judgments are created.

The evaluator's own initial implementation is bootstrapped by the explicit user instruction. It remains unconverged until real readiness, candidate judgment and merge evidence exist. Neither mock tests nor installation of this workflow count as a live Jev verdict.
